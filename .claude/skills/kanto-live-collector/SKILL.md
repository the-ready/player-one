# 関東ライブ・フェス収集タスク（週次）

## このタスクの目的

`data/lives.csv` を更新し、ダッシュボード「イベントボード」のライブ・フェスタブに、**利用者がこれから実際に行ける公演**を並べること。

このタスクが答えるべき問いは2つある。

1. **これから関東で何のライブ・フェスがあるのか**（日時・会場・出演者）
2. **それは今からでも間に合うのか**（チケットの受付状況と締切）

2つ目を落とさないことが、このタスクの成否を分ける。ライブは「公演日が先だから、まだ余裕がある」が成立しない。**公演は11月でも、先行受付の締切は今週の日曜、ということが常態である。** 公演日だけを集めた一覧は、利用者に「まだ間に合う」と誤解させる点で、無いよりも有害になりうる。

そしてもう1つ、このタスクに固有の任務がある。

3. **今週あらたに発表された公演・追加公演を検知すること**

追加公演は、一度売り切れた公演にもう一度席が出る機会であり、**このダッシュボードで最も価値の高い情報**である。発表された週に拾わなければ、次の週にはもう受付が終わっている。

## 取得してよいもの・いけないもの（着手前に読むこと）

このタスクは cron から週次で自動実行される。**「人が調べているのと同じ」ではなく機械的なアクセスである。**

1. **`robots.txt` が `Allow` している範囲だけを取得する。** サイト単位ではなく**URL単位**で見る（下記）。`<meta name="robots" content="noindex,nofollow">` や `X-Robots-Tag` を返すページも同じで、そうと分かった時点でその行は使わない
2. **収集後に拒否の意思が示されたと分かったサイトは、由来する行を消し、`data/sources.json` からも外す**
3. **利用規約で自動収集・データの二次利用を明示的に禁じているサイトは使わない**
4. **会員登録・ログインが要る領域には立ち入らない**（無料会員でも同じ）
5. **同じホストへ続けて当たらない。** `Crawl-delay` が書いてあればその秒数を空け、書いていなくても最低3秒は空ける（下記。待つのは `fetch_gate.py` の仕事で、自分で数える必要はない）
6. **1サイトあたりの取得は、その週の調査に要る分だけ**（予算制がそのままアクセス頻度の上限になっている）

1と2は礼儀ではなく、著作権法47条の5の権利制限を受けるための政令基準（著作権法施行令第7条の5）に対応する。3が別項なのは、**著作権法30条の4（情報解析）は契約を上書きしないため** —— 著作権法上適法でも、規約違反は残る。

判断に迷ったら**取らない**。理由と背景は `docs/COLLECTION-PROTOCOL.md` 第6.5節。

### 着手前：使えないサイトを一望する（検索予算を消費しない）

```bash
python3 tools/check_robots.py            # data/sources.json の調査元サイト
python3 tools/fetch_gate.py --roster venues   # 名簿のURL（この工程の主な取得先）
```

どちらも robots.txt だけを見る軽い確認（ページ本体は取得しない）なので、**検索予算を消費しない**。拒否と出たURLは今回の収集から外す。

判定は **`Claude-User`（ユーザの指示に応じたリアルタイム取得）と `Claude-SearchBot`（検索目的の巡回）の厳しいほう**を採る。学習用クローラの `ClaudeBot` とは別物で、こちらの2つがこのタスクの実行時アクセスに対応する（[Anthropicの説明](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler)）。**どちらか一方でも拒否していれば使わない**——どちらの性質のアクセスに当たるかをページ単位で言い分けられない以上、緩いほうに寄せる理由がないためである。

### 取得のたび：URLごとに判定し、間隔を空ける（自動で走る）

**サイトのトップが「OK」でも、これから開くページが `Allow` されているとは限らない。** サイトはトップを開放したまま特定のパスだけを閉じている——asoview! は `/reserve/` `/book/` `/api/` `/search/*experienceDate` を `Disallow` しており、**価格比較で開きたい予約ページはまさに閉じている側**である。

そこで `tools/fetch_gate.py` が、**これから開くURLそのもの**を取得の直前に判定する。`.claude/settings.json` の `PreToolUse` フックに登録してあるので、**`WebFetch` のたびに自動で走る**。

- **拒否されたURLはブロックされる。** そのページは開かず、同じ会場・作品の別ページ（`Allow` されているパス）を当たるか、その行を落とす。**回避しようとしないこと**
- **許可されたURLは、必要な待ち時間を消化してから通る。** `Crawl-delay`・`Request-rate`・下限3秒の最大値を空ける。**自分で数えて待つ必要はない**
- **「このホストは次の取得まで N 秒必要」と断られたら、先に別のホストを回る**（`Crawl-delay: 120` を宣言しているサイトが実在する）

手で判定したいときは直接呼べる。

```bash
python3 tools/fetch_gate.py --check <URL>   # 判定だけ（待たない・記録しない）
```

> **`curl` でページ本体を取りに行かないこと。** このゲートは `WebFetch` に掛かっている。`curl` で取るとゲートを迂回することになり、robots.txt を守っていない状態になる。

## 完走条件 —— このタスクをどう終えるか（着手前に読むこと）

**このタスクは「調べ終わったとき」ではなく、終了工程を通したときに終わる。**

### 終了工程（省略不可）

| #   | やること                                  | コマンド                                                                          |
| --- | ----------------------------------------- | --------------------------------------------------------------------------------- |
| 1   | 手元に残っている調査済みの行を書き切る    | `python3 tools/append_rows.py lives`                                              |
| 2   | ラインナップの Apple Music リンクを埋める | `python3 tools/fill_apple_music.py`                                               |
| 3   | 消えた行1件ずつに理由を付ける             | `python3 tools/prev_rows.py lives --dispose`                                      |
| 4   | 名簿を整理する                            | `python3 tools/roster.py venues --gc` と `python3 tools/roster.py festivals --gc` |
| 5   | 差分を確定する（終了コード0）             | `python3 tools/diff_data.py lives`                                                |
| 6   | 検証する（ERROR 0）                       | `python3 tools/validate_data.py`                                                  |
| 7   | 報告を出力する                            | ——                                                                                |

**この7つはすべてローカルのコマンドで、Web検索を1回も使わない。** つまり**検索の予算が尽きていても、コンテキストが逼迫していても、終了工程は必ず実行できる**。「予算が尽きたので終わります」という終わり方に、正当な理由は存在しない。

> **2 をここに置いてあるのは、これが「余裕があればやる工程」に見えるためである。** 検索を使わないので予算とは無関係だが、調査の側に置くと予算切れの回で丸ごと飛ぶ——実際にそれで全358行が空欄のまま定着した。**打ち切った週でも通す。**
>
> なお `append_lineup.py`（日割りそのものの書き出し）は調査を伴うので、この表には入らない。ただし **`--init` で `lineups.csv` を空にしたまま終えると、`lineup_id` を持つ公演行の参照が切れて 6 の検証がERRORで落ちる。** 書き出しに着手したら、そこも終わらせること。

### やってはいけない終わり方

- ❌ `--init` した後、追記が途中のまま終える（**ダッシュボードに残るのは書けた分だけ**になる）
- ❌ 調査結果をコンテキストに溜めたまま終える（追記していない行は、最初から無かったのと同じ）
- ❌ `diff_data.py` / `validate_data.py` を通さずに終える
- ❌ 「予算が尽きたのでここまでにします」と述べて、終了工程を飛ばす
- ❌ 報告を出さずに終える（**今週あらたに発表された公演・今週締切が来る受付の一覧は、このタスクの主成果である**）

> **`--init` は `data/lives.csv` を空にする。** そこから終了工程を通すまでの間、CSVは未完成の状態にある。**着手したら、必ず終了工程まで通し切ること。**
>
> 自動実行のスクリプト（`.claude/scripts/claude-routine.sh`）は、`diff_data.py` と `validate_data.py` が通らなかった回をコミットせず、`data/` を実行前の状態に戻す。**途中で終えた週は、その週の収集がまるごと失われる。** ライブでは、その週にしか拾えない追加公演・締切をまるごと落とすことを意味する。

> **「実行環境の前提」で取得ができないと判明した場合も、終了工程は通す。** その章の「最後まで実行してはならない」は、**裏の取れない行を書くな**という意味であって、CSVを未完成のまま放置してよいという意味ではない。裏の取れた行だけを書き、残りは下の撤退の手順で片付けてから、終了工程に進む。

### 撤退の手順 —— 打ち切りは「中断」ではなく「終了工程へ進むこと」

調査は打ち切ってよい。次のどれかに当たったら、**その場で探索をやめて**下の手順に入る。

- 工程ごとの枠（「調査予算」）を使い切った
- 検索の**合計が150回**に達した（枠の合計170回のうち、20回を余裕として残す）
- コンテキストが逼迫してきた
- 情報源に到達できない状態が続く（取得の失敗が連続する）

1. 調査済みで未追記の行を `append_rows.py` で書き切る
2. `python3 tools/diff_data.py lives --allow-unexplained` で、まだ処理していない前回行を出す
3. 残った行を片付ける（**ここから先は検索を使わない**）
   - まだ公演が予定されていると判断できる行 → `python3 tools/prev_rows.py lives --uid <uid>` で前回値を引き、そのまま書き戻す（tier C の持ち越し。`status`/`rank` は表示側が日付から計算するので触らなくてよい。**`onsale_*` は空欄にする**）
   - 判断できない行 → `--dispose` に `notfound` として記録する（**中止と混同しない。`cancelled` は中止を確認できたときだけ**）
4. 終了工程の 2〜7 を通す（**2 の `fill_apple_music.py` を含む。検索を使わないので打ち切りの理由にならない**）
5. 報告に「どの工程を、どの理由で打ち切ったか」「持ち越した行数」「`notfound` の件数」を書く

### 進捗を1行ずつ出す

工程が終わるたびに、次の形式の1行を出力する。自動実行のログに残り、**途中で止まったときに「どこまで進んだか」を人間が判別できる唯一の手がかり**になる。

```
[進捗] ステップ1 完了 / 追記15件（累計15件）/ 検索5回（累計5回）
```

## ⚠️ 姉妹スキルとの重要な違い（最初に読むこと）

このスキルは `/kanto-event-collector`（イベント）・`/kanto-movie-collector`（映画）と同じダッシュボードのためのものだが、**そのまま流用してはいけない箇所が4つある。**

| 項目                         | イベント収集                                         | **ライブ収集（このタスク）**                                                                                                                              |
| ---------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **価格比較**                 | 中核工程。asoview!/Klook/KKday等を横断して最安を探す | **行わない。** ライブチケットは主催者が定価を決めており、プレイガイドを横断しても価格は同じ（違うのは手数料程度）。「どこが安いか」という問いが成立しない |
| **代わりに調べること**       | —                                                    | **チケットの受付経路と受付期間を「時刻まで」。** いつ発売され、いつまでに申し込めるか                                                                     |
| **公演ごとの差**             | 同じイベントは1行                                    | **ツアーは公演ごとに販売状況が違う。** 一部の公演にだけ出る枠（見切れ席・追加席・公式リセール）を `limited_sale` に記録する                               |
| **画像**                     | 収集しない                                           | **収集しない**（理由は下記「画像を収集しない」章。3タブとも画像の列を持たない）                                                                           |
| **前回データとの突き合わせ** | 共通工程（3スキルとも実施する）                      | **同じ仕組みを使うが、意味が重い。** 追加公演・新規発表の検知そのものがこのタスクの主成果になる                                                           |

**価格比較の工数をまるごと「受付期間の確定」と「追加公演の検知」に振り替える**、というのがこのスキルの設計である。

## 実行環境の前提（着手前に確認すること）

このタスクは**公演ページを実際に開いて読むこと**を前提にしている。検索結果の要約だけでは、日付・時刻・受付期間を規則どおりに確定できない。

着手前に、次の2つができるかを確認する。

1. アーティスト公式サイト・会場公式サイト・正規プレイガイドの**ページ本文を取得できる**か
2. 音楽メディア（音楽ナタリー等）の記事本文を取得できる

**取得できない環境では、このタスクを最後まで実行してはならない。**（これは「裏の取れない行を書くな」という意味であって、CSVを未完成のまま放置してよいという意味ではない。書ける行だけ書き、「完走条件」の撤退の手順で残りを片付けてから終了工程に進む。） 検索結果の要約は公演名と日付の対応を取り違えることがあり（下記ステップ1の警告を参照）、それを根拠に書くと、実在するアーティストの公演日を間違えて掲載することになる。

取得できない場合は、**裏の取れた公演だけを書き、件数が目標に届かないことと理由をそのまま報告する**こと。目標件数に合わせるために未検証の行を足すのは、このタスクで最もやってはいけない失敗である。

## 出力仕様

### 出力先

- **`data/lives.csv`**（全件を毎回書き直す。追記ではなく完全再生成）
- **`data/lineups.csv`**（フェスの日割りラインナップ。同じく毎回書き直す。後述の「フェスの日割りラインナップ」章）
- `index.html` はこのタスクでは編集しない
- `data/venues.csv`（会場の名簿）も更新する。以前は「追加候補として報告し、追加は人間に委ねる」としていたが、名簿はスキーマ検証つきのデータなので `tools/roster.py` 経由で**直接更新してよい**（新会場は `candidate` として登録され、2回ヒットすると `active` に昇格する）。手順はステップ1と `docs/COLLECTION-PROTOCOL.md` 第7章を参照
- **ただしSKILL.md（この文書）は書き換えない。** 名簿（データ）は自動更新、ルール（散文）は提案止まりという線を守ること。ルールを変えたほうがよいと気づいたら `docs/skill-feedback.md` に追記する

> **書き出し先に注意**: ダッシュボードは `data/lives.csv` しか読まず、別パスへのフォールバックを意図的に持たない。リポジトリのルート直下に `lives.csv` を書いても反映されない。

### 出力方法（CSV書き出しの手順）

全件を最後にまとめてCSVに書くのではなく、調査の区切りごとにバッチで追記する。**全件を調査結果としてコンテキストに溜め込んでから最後に一括生成する、という進め方はしないこと。**

1. `python3 tools/append_rows.py lives --init` を実行し、`data/lives.csv` をヘッダーだけの状態にする。**前回の内容は `data/.prev/` に自動退避される**ので、差分検知の材料は失われない（以前は初期化の前に読む必要があったが、その制約は無くなった）
2. 5〜10件の調査が完了するごとに、結果をまとめて以下の形式でCSVに追記する

   ```bash
   python3 tools/append_rows.py lives <<'EOF'
   {"title": "...", "artists": "...", "venue": "...", ...}
   {"title": "...", "artists": "...", "venue": "...", ...}
   EOF
   ```

3. コンテキストに全件のデータを保持する必要はない。追記が終わったバッチの内容は忘れてよい（差分は `diff_data.py` が機械的に取るので、手元に抱える必要もない）
4. `id` はスクリプトが自動採番する。JSONに含める必要はない
5. JSONに含めない列は空文字で補完される。分かっている列だけを渡せばよい
6. 全件の調査・追記が終わったら `python3 tools/diff_data.py lives` と `python3 tools/validate_data.py` を実行する

自然なバッチの区切りの例：

- 会場リストを5〜10会場調べたらまとめて書く
- 関東開催フェスの名簿を確認したらまとめて書く
- 調査ステップが変わる節目（会場調査→フェス調査→プレイガイド補完）でまとめて書く

#### 前回から変わっていない列は書き直さない（持ち越し）

会場の座標・最寄り駅・駐車場・読みは、前回値から自動で補完される。**空欄のまま渡してよい。**同じ会場の別の公演からも引かれるので、ツアーで同じ箱が何度も出てくる場合でも書くのは1回でよい。

内容にも変更がないことを**確認できた**行は、`"_carry": "*"` を添えると `desc` `artists` `official_url` `apple_music_url` なども前回値で埋まる。

```bash
python3 tools/append_rows.py lives <<'EOF'
{"title": "...", "venue": "Kアリーナ横浜", "start_date": "2026-09-05", "end_date": "2026-09-05",
 "open_time": "16:00", "start_time": "17:00",
 "genre": "rock", "live_type": "oneman", "area": "神奈川県・横浜市西区",
 "pref": "kanagawa", "price": "全席指定 9,800円", "source": "チケットぴあ", "url": "https://...",
 "onsale_label": "一般発売", "onsale_start": "2026-08-09", "onsale_start_time": "10:00", "_carry": "*"}
EOF
```

> **受付・日付・料金は持ち越せない。** `onsale_end` などを `_carry` に指定するとスクリプトがエラーで落ちる。これは「❌ 前回CSVの `onsale_end` をそのまま流用する」という後述の禁止事項を、指示文でのお願いではなく仕組みで担保したものである。**受付は進む。** 確認できないなら空欄にする。
>
> `"_carry": "*"` を使ってよいのは、その行の内容に変更がないことを**実際に確認できたとき**だけ。ライブでは出演者の追加・キャンセルが起きるので、`artists` の持ち越しには特に注意する。

### CSV列（この順序・この列名を厳守）

```
id,tour_id,title,kana,artists,genre,live_type,area,venue,venue_url,pref,start_date,end_date,date,dates,open_time,start_time,end_time,date_note,backup_date,status,rank,announced_date,is_additional,onsale_label,onsale_start,onsale_start_time,onsale_end,onsale_end_time,limited_sale,price,source,url,official_url,lat,lng,desc,note,parking,nearest_station,apple_music_url,lineup_id
```

全42列。列名・順序ともに厳守すること（`kana` が増え、`venue_url` の位置が `venue` の隣に移り、末尾に `parking` `nearest_station` `apple_music_url` `lineup_id` が加わった）。

#### 日程の書き方（3つの収集スキルで共通）

**画面に出る日付の文字列も、`開催中` `まもなく開催` といった開催状況のバッジも、
ダッシュボードが表示のたびに組み立てる。** ここで書くのは、機械が読める事実だけである。

| 列                | 規則                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dates`           | **飛び日程**（連続していない複数日）の実開催日を `\|` 区切りで全部並べる。例：`2026-08-10\|2026-08-11\|2026-08-14`。**連続した会期では空欄**（開始日〜終了日で足りる）。書くときは先頭を開始日と、末尾を `end_date` と一致させること。**この列があると、開催しない日は「本日は休み」と表示され、日程の絞り込みからも外れる**                                                                                                                                              |
| `open_time`       | 開場時刻 `H:MM`。無ければ空欄                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `start_time`      | 開演時刻 `H:MM`。無ければ空欄                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `end_time`        | 終了時刻 `H:MM`。無ければ空欄                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `date_note`       | 上のどれにも収まらない但し書き（例：`オールナイト` `土日祝のみ` `1週間限定` `毎朝10時開始`）。**日付や時刻そのものをここに書き写さない**——構造化列に入れれば画面が組み立てる                                                                                                                                                                                                                                                                                              |
| `backup_date`     | **予備日**（雨天・荒天で順延したときの日）を `\|` 区切りで。**会期には含めない**——本開催で終わればこの日は使われないので、`end_date` を1日延ばすと「まだやっている」と嘘をつくことになる。カードの日付欄ではなく「くわしく」の中に出る。**予備日の当日は「本日予備日」バッジが出る**ので、順延が実際に起きたら開始日・終了日を新しい日に書き換えてこの列を空にすること                                                                                                    |
| `date`            | **原則として空欄。** ISOの日付に落とすと持っていない精度を騙ることになる日程（`2026年10月中旬〜下旬（見頃予想）` `8月の毎週土日` など）だけ、ここに自由記述で書く。**書いた行はこの文字列がそのまま表示され、上の構造化列は使われない**。**ただし月・季節までは読み取れる場合、`start_date`/`end_date` にはその月・季節をまるごと設定すること**（下記「幅のある予測日程」参照）——空欄のままだと日程の絞り込みが「無期限」として扱い、無関係な日で絞っても表示されてしまう |
| `status` / `rank` | **原則として空欄。** 日付から毎回計算される。開始日も `end_date` も持たない行——つまり `date` に自由記述を書いた行——でだけ、下の表から選んで書く                                                                                                                                                                                                                                                                                                                           |

以前は `date` に `2026.9.5(土) 開場16:00／開演17:00` のような表示用の文字列を、`status` に収集を実行した日の
判定を書いていた。やめた理由は2つある。

- **書き手ごとに表記がそろわなかった。** 同じ会期が `2026.8.1〜9.30` にも
  `2026-08-01〜2026-09-30` にも `2026年8月1日〜9月30日` にもなり、曜日の有無も
  行ごとに違っていた。毎週ゼロから書き起こす以上、書式を決めても必ず崩れる。
- **収集した日で時間が止まっていた。** 週の後半に見た人には、始まっている公演が
  「まもなく開催」のままで、終わった公演が「開催中」のまま残る。
  データが古いほど、画面の嘘が増えていく。

どちらも「計算できる値を、計算せずに書き置いた」ことが原因である。
書いた値が画面に出ないのは気持ちが悪いかもしれないが、**書かないほうが正しい**。

##### 幅のある予測日程（「10月中旬〜下旬」「2026年夏」など）は、`date` だけでなく `start_date`/`end_date` も埋める

`date` に自由記述を書く行のうち、**月・季節までは読み取れる**もの（「10月中旬〜下旬」「2026年夏」）は、
`start_date`/`end_date` を空欄のままにしてはいけない。空欄は「本当に何も分からない」という意味になり、
表示側は「不明な端は制約なしとみなす」規則で扱うため、**日程の絞り込みが一切効かなくなる**
——10月開催のイベントが8月の日付で絞っても一覧に出てしまう。

代わりに、読み取れた月・季節を**まるごと** `start_date`/`end_date` に設定する。
「中旬〜下旬」を月全体に広げるのは精度を落とす丸めだが、
「本当は10月なのに9月と誤って除外する」より「10月中は多めに表示される」ほうが実害が小さい。

| 読み取れた期間 | `start_date` | `end_date`   |
| -------------- | ------------ | ------------ |
| 10月中旬〜下旬 | `2026-10-01` | `2026-10-31` |
| 2026年夏       | `2026-06-01` | `2026-08-31` |

`date` 列の表示（「2026年10月中旬〜下旬（見頃予想。開花状況により変動）」）はそのままでよい。
`start_date`/`end_date` を埋めた行は `status`/`rank` を空欄に戻すこと（日付から自動で計算される）。

**月すら読み取れない行**（「会期は公式サイト参照」）は、これまでどおり両方空欄のままにする。
読み取れる情報が無いところに月を割り当てるのは、それこそ憶測になる。

`python3 tools/validate_data.py` は、`date` に「◯月」「春」「夏」「秋」「冬」を含む自由記述があるのに
`start_date`/`end_date` が両方空の行を WARNING で挙げる。出たら必ずこの手順に従うこと。

## 収集ルール

### 1. 対象期間 —— 「公演日」または「締切」のどちらかが3ヶ月以内

イベント収集スキルの「直近3ヶ月」とは条件が違う。**次のどちらかを満たすものを対象とする。**

- ✅ **公演日**が実行日から3ヶ月以内
- ✅ **チケットの受付締切または一般発売日**が実行日から3ヶ月以内（公演日が3ヶ月より先でもよい）

**理由**: 半年先の公演のチケットが今日売られている、というのがライブの通常の姿である。公演日だけで切ると、**今まさに申し込むべき公演が一覧から消える**。このダッシュボードは「行けるものを探す」ためのものであり、「行動すべきタイミング」を落としてはならない。

除外するもの：

- ❌ すでに終了した公演
- ❌ 公演日が3ヶ月より先で、**かつ**チケットの受付予定も3ヶ月より先のもの（まだ何もできない）

### 2. 対象地域は関東1都6県＋隣接5県

| 区分                   | 都県                                                     | `pref` 列                                                        |
| ---------------------- | -------------------------------------------------------- | ---------------------------------------------------------------- |
| **本体（関東1都6県）** | 東京都・神奈川県・埼玉県・千葉県・茨城県・栃木県・群馬県 | `tokyo` `kanagawa` `saitama` `chiba` `ibaraki` `tochigi` `gunma` |
| **隣接県**             | 山梨県・静岡県・長野県・新潟県・福島県                   | すべて `other`                                                   |

隣接県を含めるのは、**関東からその日のうちに行ける公演が実際にあり、名簿にもその会場が
意図的に入っている**ためである（`data/venues.csv` の静岡県18会場、`data/festivals.csv` の
FUJI ROCK FESTIVAL＝新潟県）。「隣接5県」は関東のいずれかの都県と県境を接する県、という
定義で決めてある——恣意的に増やさないための線引きなので、**この5県より外へは広げない**。

> **`pref` は8キーしかない。** 隣接県はすべて `other`（関東以外）になる。`shizuoka` の
> ような県名を書くと `roster.py` と `validate_data.py` が拒否する。**県名は `area` 列に人間向けの
> 表記で書く**（例：`area` = `静岡県・浜松市`、`pref` = `other`）。画面では「関東以外」の
> チップで絞り込める。

ツアーは、この12都県で行われる公演だけを拾う。同じツアーの大阪公演・名古屋公演は入れない
（`tour_id` は同じでよいが、行としてこの範囲の分のみ書く）。

### 3. ツアーは「1公演＝1行」（重要）

**ツアー全体を1行にまとめてはならない。** `venue` に会場を1つしか書けず、このダッシュボードの主機能である**場所での絞り込みが壊れる**（「東京公演」と「横浜公演」が1行になると、横浜で検索しても出てこない、あるいは逆に東京で検索して横浜公演が出てくる）。

- ✅ 同じツアーの東京公演・横浜公演・さいたま公演 → **3行**に分け、`tour_id` を共通にする
- ✅ **同一会場での連日公演**（2〜3日）→ **1行**にまとめ、`start_date`/`end_date` で表現してよい
- ✅ 複数日開催のフェス → **1行**（`start_date`/`end_date`）
- ❌ `venue` に `東京ドーム|横浜アリーナ` のように複数会場を書く

### 4. 目標件数

**80〜150件**を目安とする。

バランスの取り方：

- **関東7都県すべてから最低3件。** 東京は全体の半分まで
- **隣接県（`pref="other"`）は、この7都県の枠を埋める代わりにはならない。** 関東が薄いまま隣接県で件数を稼ぐと、このダッシュボードが「関東のイベントボード」でなくなる。**全体の1割程度を上限の目安**とし、それを超えそうなら関東側の探索が足りていないと考えること
- **ジャンル10種のうち最低7種**をカバーする
- **会場規模を散らす。** ドーム・アリーナ級だけを集めると「有名アーティストの一覧」になり、発見の価値が落ちる。**ホール級・ライブハウス級を全体の1/3以上**入れること
- `live_type` は `oneman` に偏りやすい。`fes` `event` `classic` `free` も意識的に探す

### 同じことを二度調べない —— 打ち切りの基準

**必須列が揃った行は、そこで調査を終える。** すでに「行けるか・間に合うか」を判断できる情報が揃っているのに調べ続けるのは、品質ではなく消費である。

| 区分                          | 列                                                                                                                                                   | 扱い                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **これが揃ったら終わり**      | `title` `artists` `genre` `live_type` `area` `venue` `pref` `start_date`/`end_date` `price` `source` `url` `desc` ＋ **確認できた範囲の `onsale_*`** | 揃った時点で次の行へ移る                                             |
| **ついでに拾うだけ**          | `kana` `note` `venue_url` `tour_id` `announced_date` `is_additional` `parking` `nearest_station`                                                     | 開いたページに書いてあれば書く。**このために追加でページを開かない** |
| **調べない**                  | `lat` / `lng`                                                                                                                                        | `venues.csv` と前回値から自動で補完される。**空欄で渡す**            |
| **1回で見つからなければ空欄** | `apple_music_url`（`lives.csv` 側）                                                                                                                  | iTunes Search API を1回叩いて確信が持てなければ空欄。粘らない        |

**具体的にやってはいけないこと**

- ❌ ツアーの各公演について、同じ会場の駐車場・最寄り駅を毎回調べ直す（会場の属性として自動補完される。**書くのは1公演ぶんでよい**）
- ❌ 会場ページで日時・料金・受付を確認した後、座標のためにもう一度地図を開く
- ❌ `kana` や `tour_id` が分からないので検索する（分からなければ空欄が正しい）
- ❌ **すでに `onsale_label` が `SOLD OUT` と確認できた公演について、他の受付経路を探し続ける**（完売は確定情報である。公式リセールの有無は会場・ツアーページで分かった範囲だけ書く）
- ❌ 価格比較（このタブでは**行わない**。定価固定のため——「姉妹スキルとの重要な違い」参照）

### 予算が尽きたら、何を捨てるか

上から守り、**下から捨てる**。

1. **tier A の再確認**（落とすと中止を伝えられない。ライブでは最も実害が大きい）

4. 新規行の深掘り
5. tier B の再確認
6. **補助列の穴埋め（`lives.csv` の `apple_music_url`、`parking`、`kana` 等）** ← 最初に捨てるのはここ

ローカルのコマンド（`tools/fill_apple_music.py`）なので、予算切れを理由に飛ばさない。**

**目標件数（80〜150件）に届かないことより、未検証の行を足すことのほうが重い失敗である。** これは「実行環境の前提」章がすでに述べているとおりで、予算切れでも同じことが言える。打ち切ったら、その事実と工程名を報告に書く。

### ステップ1：会場ベースの網羅調査（最優先）

調査対象の会場は `data/venues.csv` にある。

```bash
python3 tools/roster.py venues --list --urls                  # 全件（隣接県も含む）
python3 tools/roster.py venues --list --pref tokyo --urls     # 都県で絞る
python3 tools/roster.py venues --list --pref other --urls     # 隣接県だけ（静岡ほか）
python3 tools/roster.py venues --list --kind livehouse --urls
```

> **都県ごとに回すときは `--pref other` を忘れないこと。** 隣接県の会場は
> `pref="other"` で入っているので（対象地域の節を参照）、関東7都県を順に指定するだけでは
> **1件も出てこない**。名簿を漏れなく一周したいなら `--pref` を付けずに全件出すのが確実である。

（`retired` の会場と**休館中の会場は自動的に除かれる**。以前このSKILL.mdに直接書いていた「さいたまスーパーアリーナは改装休館中」といった情報は、`venues.csv` の `closed_until` 列に移した。散文に書くと更新されないまま古くなるため）

**4列目に会場の公式サイトURLが出る。この工程では、そのURLを直接開く（検索しない）。** 72件すべてにURLが入っているので、**この工程の検索の枠は5回**——名簿に新しく足した会場のぶんだけである。

**1会場につき1回、その箱のスケジュールを調べる。そのとき次の3つを同時に済ませる。**

1. **前回分の照合** —— ステップ0の一覧でその会場の行を確認し、**まだ予定されているか／中止・延期になっていないか／受付が次の段階に進んでいないか／追加席が出ていないか**を見る
2. **新規の発見** —— 前回になかった公演を拾う
3. **収穫の記録** —— `python3 tools/roster.py venues --hit {会場名}`

> **行を1件ずつ再確認してはいけない。** 会場の公演カレンダーを1回開けば、既存行の確認と新規の発見は同じ取得で終わる。

新しい会場・閉館した会場を見つけたら、その場で名簿に反映する（以前は「報告して人間の判断に委ねる」としていたが、名簿はスキーマ検証つきのデータなので直接更新してよい）。

```bash
python3 tools/roster.py venues --add <<'EOF'
{"venue": "○○アリーナ", "kind": "arena", "pref": "chiba", "area": "千葉県・千葉市",
 "capacity": "10000", "lat": "35.60", "lng": "140.10", "url": "https://..."}
EOF
python3 tools/roster.py venues --retire ○○ホール --reason "2026年6月閉館"
python3 tools/roster.py venues --block ○○ホール --reason "robots.txt が拒否"  # 閉館ではない
python3 tools/roster.py venues --close ○○アリーナ --until 2027-04-01 --reason "改修工事のため休館"
```

`kind` は `dome` `arena` `hall` `livehouse` `outdoor` から選ぶ。**収集元のページの文言を `note` にそのまま持ち込まないこと**（`roster.py` が指示文めいた文字列を拒否するが、そもそも入れない）。

**会場公式サイトの公演カレンダーを最優先の情報源とする。** 理由は、それが「その箱で何月何日に何があるか」の一次情報であり、**このダッシュボードの2大絞り込み軸（日付と場所）に直結する情報が、最も正確な形で載っている**ためである。まとめサイトは日付が古く、プレイガイドは受付が始まった公演しか載らない。

> ⚠️ **会場スケジュールは「候補の発見」にだけ使い、そのまま書き写さないこと。**
> 実際の収集で、会場単位のスケジュール要約は**公演名と日付の対応がずれる**ことが繰り返し確認された（同一会場で12日連続公演と別公演が同じ日に立つ、季節の合わない公演名が混ざる、など）。
> 会場スケジュールで拾った公演は、**必ずステップ5で公演名を軸に検索し直して、日付・会場・時刻を裏取りしてから書く**。裏が取れなければその行は落とす。

> **休館中の会場について**: 長期休館・建て替え中の会場には公演が組まれないので、調査しても収穫がない。`roster.py venues --list` はこれらを自動的に除いて出すので、リストに出てこない会場は調べなくてよい。新たに長期休館を知ったときは `roster.py venues --close {会場名} --until {再開予定日}` で名簿に記録すること（このSKILL.mdには書かない。散文に書いた休館情報は、再開しても更新されないまま残る）。

検索クエリの組み立て方：

検索クエリの組み立て方（**名簿に `url` が無い会場に限る**。URLが分かっている会場は直接開く）：

```

{会場名} イベントスケジュール
{会場名} ライブ {実行年}年{実行月}月
```

例：

- `Kアリーナ横浜 公演スケジュール 2026年9月`

**スポーツ・展示会・株主総会などの非音楽イベントは拾わない。** このタブは音楽公演のためのものである。ただし「アイドルの握手会・ファンミーティング」は、音楽公演を伴う場合のみ対象としてよい。

### ステップ4：追加公演・新規発表の検知（このタスク固有の工程）

**音楽メディアの「追加公演」記事を毎回定点観測する。**

検索クエリ例：

```

```

そのうえで、**機械的に取った差分と突き合わせる。**

```bash
python3 tools/diff_data.py lives --allow-unexplained
```

前回との突き合わせを目視でやってはいけない。103行×35列を読み直すことになるうえ、見落としても誰も気づけない。**突き合わせは機械の仕事で、この工程でのモデルの仕事は、機械が拾った差分の意味を判断すること**である。

| `diff_data.py` の出力             | やること                                                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **[新規]** に出た行               | `announced_date` を確定する（下記）                                                                                           |
| 既存の `tour_id` に増えた公演     | `is_additional = 1`                                                                                                           |
| **[変更]** に `onsale_*` が出た行 | 受付が次の段階に進んだということ。値が正しく更新されているか確認する                                                          |
| **[変更]** に `artists` が出た行  | フェスの出演者追加。`desc` のラインナップも書き換えたか確認する                                                               |
| **[表記が変わった可能性]**        | 同じ公演なら `--dispose` に `renamed` を記録する（放置すると同じ公演が「消滅1件＋新規1件」に数えられ、NEWバッジが誤って付く） |
| **[消滅]** の行                   | 1件ずつ理由を記録する（下記）                                                                                                 |

**消えた行には必ず説明をつける。**

```bash
python3 tools/prev_rows.py lives --dispose <<'EOF'
{"uid": "3f2a1b9c", "status": "ended",     "note": "公演終了"}
{"uid": "8d7e6f50", "status": "cancelled", "note": "アーティスト体調不良により公演中止（公式発表）"}
{"uid": "a1b2c3d4", "status": "notfound",  "note": "会場スケジュールから消えており、中止か延期か確認できず"}
EOF
```

> **中止・延期はライブで最も起きやすく、最も実害の大きい変化である。** 前回にあった公演が今回無いとき、それを黙って落とすと、中止を知らない利用者が会場に行くことになる。`cancelled` と `notfound` を区別して記録し、**どちらも報告に含めること**。

`announced_date` は、**メディアの発表記事の日付が分かればその日付を使う**。分からない場合に限り、差分で新規と判定された行に今日の日付を入れる。**分からないまま推測で古い日付を書かない。**

**公演名そのものに「追加公演」と入っている場合**（例：`ano Hall Tour 2026 DUAL DINER 追加公演`）は、差分を取るまでもなく主催者が追加公演だと言っているので、`is_additional=1` にしてよい。初回実行時（前回データが存在しないとき）に追加公演を拾える唯一の手がかりでもある。

> **初回実行時の注意**: 前回データが無い状態では、差分による追加公演の検知は原理的に成立しない（`diff_data.py` は「前回データなし」と表示する）。初回は `is_additional` が上の「タイトルに明記された分」だけになるのが正しく、**それらしく見せるために推測で立ててはならない**。2回目以降から本来の検知が働く。

### ステップ5：各公演の深掘り

**この工程の枠は75回**（「調査予算」参照）。**枠を使ってよいのは新規行だけ**である。前回から続く行は、前回の `url`（チケットページ）と `official_url` を直接開けば検索は要らない。

拾った公演1件ごとに、**必ず公式情報またはプレイガイドの公演ページまで辿って**以下を確定させる。まとめサイトの記載だけで済ませない。

1. **正確な公演日**と**開場・開演時刻**
2. **会場の正式名称**（`venues.csv` と突き合わせる。表記ゆれに注意：`Zepp DiverCity` と `Zepp DiverCity(TOKYO)` など）
3. **出演者**（フェスは主要8組まで）
4. **チケットの受付状況** — いま何次先行まで進んでいるか、直近の締切はいつか、一般発売はいつか
5. **券種別の料金**（ドリンク代別かどうかも確認する）
6. **公式サイトURL**
7. **注意事項** — 全席指定/オールスタンディング、年齢制限、再入場、雨天決行
8. **駐車場・最寄り駅** — 「駐車場・最寄り駅の書き方」参照（**初出の会場のみ**）
9. **メインアーティストの Apple Music アーティストページ** — 「Apple Music アーティストリンク」参照（**API1回**）

**1〜7は、原則としてプレイガイドの公演ページ1回の取得で揃う。** 項目ごとにページを開き直さないこと。

#### 深掘りを打ち切る基準

**必須列（`title` `artists` `genre` `live_type` 場所 日付 `price` `source` `url` `desc` ＋確認できた範囲の `onsale_*`）が揃った時点で、その行の調査を終える。**

とくに次の状態は**確定情報**なので、それ以上の経路を探さない。

- `onsale_label` = `SOLD OUT`（完売）→ 公式リセールの有無は、開いたページに書いてあった範囲だけ `note` / `limited_sale` に書く。**別経路を探しに行かない**
- 全受付が終わっており、次の受付が未定 → `onsale_*` を空欄にして終わり。**過去の受付を掘り返さない**（「過去の受付しか分からないときは空欄」という規則のとおり）
- `apple_music_url` が iTunes Search API 1回で確信を持てない → 空欄で確定。**別の綴りで再検索しない**

**ツアーの2公演目以降は、1公演目で確定した内容を使い回す。** 会場・駐車場・最寄り駅・アーティスト・Apple Musicリンクは公演ごとに変わらない。**公演ごとに確認し直すのは、受付状況（`onsale_*`）と限定枠（`limited_sale`）だけ**である——これはツアー内で公演ごとに違うので、確認する価値がある（「限定・追加販売」章）。

## チケット情報の記載規則

### 転売サイトの絶対禁止（最重要）

> **`url` に入れてよいのは、正規の販売経路のみである。二次流通・転売サイトを、価格に関係なく採用してはならない。**

ライブチケットの検索では、転売サイトが検索結果の上位に来ることが頻繁にある。イベント収集より事故の確率が桁違いに高い。

**`url` に入れてよいもの**

- 公演・ツアー・フェスの公式サイトのチケットページ
- チケットぴあ／イープラス／ローソンチケット／楽天チケット／ticket board／LivePocket／ZAIKO／teket などの正規プレイガイド
- アーティストのファンクラブ受付ページ（会員限定である旨を `note` に書く）

**`url` に入れてはならないもの**

- 二次流通・リセールを謳う非公式サイト
- オークション・フリマサービスの出品ページ
- 「定価より安い」ことを訴求するチケット売買仲介サイト

**公式リセール**（チケット流通センターではなく、**主催者・プレイガイドが公式に運営する**リセール。チケトレ、ぴあ公式リセール、e+ リセール等）は、`url` にはせず **`note` に「公式リセール受付中」と書く**。あくまで補足情報として扱う。

### 受付期間（`onsale_*`）の書き方 —— 日付だけでなく**時刻まで**取る

**直近の、いま利用者が申し込める受付**を1つ選んで書く。複数の先行が並行している場合は、**締切が最も近いもの**を選ぶ。

```
onsale_label      = オフィシャル先行
onsale_start      = 2026-08-01
onsale_start_time = 10:00
onsale_end        = 2026-08-10
onsale_end_time   = 23:59
```

#### なぜ時刻が必須級なのか

**先着順の販売では、時刻こそが情報の本体である。**「8月1日発売」とだけ書かれた一覧は、実質的に役に立たない。人気公演は発売時刻の数分で売り切れるので、`10:00` を知らないと並べない。

ダッシュボードは**時刻まで含めて「発売前／受付中／受付終了」を判定する**。日付だけを書くと開始は 0:00、締切は 23:59 とみなされるため、

- 開始時刻を落とすと → 発売当日の朝に見た人へ「もう発売中」と嘘をつく
- 締切時刻を落とすと → `18:00` 締切の受付を、その日いっぱい受付中に見せる

いずれも「間に合うと思って開いたら終わっていた」を生む。**日付が分かって時刻が分からないときは、時刻列を空欄にする**（推測で `10:00` と書かない）。空欄なら上の安全側の解釈が働く。

#### 時刻はどこに載っているか

- プレイガイドの公演ページ（受付ごとに「受付期間 8/1(土)10:00〜8/10(日)23:59」の形で載る）
- アーティスト公式サイトのチケットページ・お知らせ記事
- ファンクラブ先行の告知（会員向けページに時刻まで書かれることが多い）

「◯時頃」としか分からない場合は、**その旨が確認できた時刻をそのまま書き、`note` に「発売時刻は公式で最終確認を」と添える**。

すでに全受付が終わっている、または売り切れている場合は、状態を `onsale_label` に書き、日付は空欄にする。

```
onsale_label = SOLD OUT        （完売。公式リセールがあれば note に書く）
onsale_label = 受付終了        （受付期間が終わり、次の受付が未定）
onsale_label = 当日券あり
onsale_label = 入場無料
```

**完売公演も一覧には載せる。** 公式リセールや当日券の可能性があり、「そもそも何をやっているか」自体が情報だからである。ただし `onsale_label` を必ず `SOLD OUT` にして、**取れるように見せてはならない。**

> **過去の受付しか分からないときは、`onsale_*` を空欄にする。** 「6月の一般先行が6/14に終了した」ことだけを確認して `受付終了` と書くと、その後に始まった受付を見落として「もう買えない」と誤って伝えることになる。**いま有効な受付が確認できたときだけ書く**のが原則で、確認できなければ空欄が正しい。

### 限定・追加販売（`limited_sale`）—— ツアーは公演ごとに販売状況が違う

**ツアーでは、一部の公演にだけ枠が出ることが頻繁にある。** ステージ構成が固まって見切れ席が解放される、機材席が客席に転用される、完売公演にだけ公式リセールが立つ——いずれも**特定の日程・特定の会場にだけ起きる**。

これは利用者にとって最大級の価値がある情報である。「東京は完売だが、横浜公演だけ追加席が出た」を知らせられるかどうかが、このダッシュボードの存在意義に直結する。

#### `limited_sale` に書くもの

| 対象                   | 例                                                                    |
| ---------------------- | --------------------------------------------------------------------- |
| 見切れ席・注釈付指定席 | `見切れ席を2026.8.1(土)10:00より追加販売`                             |
| 追加席・機材開放席     | `機材開放席を2026.9.3(木)18:00より販売`                               |
| 公式リセール           | `公式リセール（抽選）2026.8.25(火)16:00〜9.1(火)16:00 出品・購入申込` |
| 当日券                 | `当日券を開演1時間前より会場窓口で販売`                               |
| 特定公演限定の券種     | `この公演のみ着席指定席を用意`                                        |

**内容と日時をセットで1文に書く。** 日時のない「追加席あり」は、いつ動けばいいのか分からず役に立たない。

#### 書き方の規則

1. **公演ごとに確認する。** ツアーの1公演で見つけたからといって、他の公演の行にコピーしてはならない
2. 逆に、**ツアー全体に共通する案内（ツアー公式リセールなど）は、該当する全公演の行に書く**。1行にだけ書くと「この公演だけ特別」と誤読される
3. 二次流通は書かない。**公式リセール（チケトレ／ぴあ公式リセール／e+リセール／チケプラTrade等、主催者・プレイガイドが運営するもの）に限る**
4. 確認できないものは空欄。「たぶん当日券が出る」は書かない

#### 調査手順

前回CSVとの突き合わせ（ステップ4）と同じタイミングで、**`tour_id` 単位で全公演を横に並べて見る。**

```
tour_id ごとに、関東の全公演について
  ├ 受付状況（onsale_label / onsale_start / onsale_end）
  └ 限定枠の有無（limited_sale）
を並べ、公演ごとに違いがあるかを確認する
```

違いがあること自体が発見なので、**報告時に「ツアー内で販売状況が分かれている公演」を明示する**こと。

検索クエリ例：

```
{アーティスト名} 見切れ席 販売
{アーティスト名} {会場名} 追加席
{アーティスト名} 公式リセール {実行年}
{フェス名} リセール 受付
{ツアー名} 当日券
```

### ⚠️ 日付・時刻・料金の絶対規則

> **確認していない日付・時刻・締切・料金を絶対に書かないこと。空欄のままにすること。**

ライブは**単日・時刻指定**であり、間違いがイベント以上に直接的な実害になる。「開演19:00と書いてあったので18:30に着いたら、実際は18:00開演だった」は取り返しがつかない。

**禁止事項**

- ❌ 「同じツアーの他会場が19:00開演だから、ここも19:00だろう」という推定
- ❌ 「先行はだいたい2週間前に締め切る」という相場からの推測
- ❌ 前回CSVの `onsale_end` をそのまま流用する（受付は進む）
- ❌ 券種を確認せずに「一般〇〇円」とだけ書く
- ❌ 発表日が分からないのに `announced_date` を埋める

**空欄が多いことは品質の問題ではない。誤った締切が1件混ざることのほうが、はるかに深刻な品質問題である。**（ダッシュボード側は、どの列が空でも壊れないように作られている）

## 画像を収集しない

> **アーティスト写真（アー写）・ツアーキービジュアル・フェスのポスター/フライヤー画像のURLを、収集してはならない。**

`data/lives.csv` に画像URLの列は存在しない。列を勝手に追加してもいけない。

**理由**：権利者が出しているのは自社サイトへ掲載するための許諾であって、第三者サイトへの再掲載や画像への直リンクの許諾ではない。芸能事務所・レーベルは公式サイトで**アーティスト画像の無断転載を明示的に禁止**しており、さらに**直リンク（ホットリンク）を禁止しているケースが実在する**。「ファイルを複製せずURL参照するだけ」という論理は、著作権侵害の局面では概ね通っても、利用規約違反と著作者人格権（氏名表示権）の問題を何も片付けない。この判断は3タブに共通で、映画のポスターも同じ理由で扱わない。

詳細な判断の根拠は `docs/DESIGN.md` 第7.1節に記載してある。**方針を変更する場合は、必ずそこを先に読むこと。**

画像の代わりに、ダッシュボードは複数出演（フェス・共演）の公演で `artists` 列の出演者名をタイトル直下にテキストで並べる。文字は事実情報なので権利上の制約がなく、フェスにおいては小さく表示された画像よりも情報量が多い（画像からは出演者を読み取れない）。したがって、**`artists` 列を丁寧に埋めることが、カードの情報量に直接つながる**。ここは手を抜かないこと。

## 駐車場・最寄り駅の書き方（`parking` / `nearest_station`）

「くわしく」を開いた利用者が、車で行くか電車で行くかをその場で判断できるようにするための情報。**会場公式サイトの「アクセス」ページに載っている内容をそのまま書き写す**（憶測で埋めない）。

| 列                | 書き方                                                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `nearest_station` | 最寄り駅名と徒歩時間（例：`国際展示場駅（徒歩7分）`）。使える駅が複数あるときは `／` 区切りで併記してよい                                             |
| `parking`         | 駐車場の有無・台数・料金（例：`あり（有料・300台）`、`契約駐車場なし（近隣コインパーキングを利用）`）。専用駐車場が無い会場は「無い」という事実を書く |

### 同じ会場について、二度調べない・二度書かない

駐車場・最寄り駅は**「行の属性」ではなく「会場の属性」**なので、`append_rows.py` が同じ会場の別の行から自動で補完する。**前回の `lives.csv` にある会場も、今回このセッションで既に書いた会場も、どちらからも引かれる。**

- ツアーの2公演目以降 → **空欄で渡す。自動で埋まる**
- 前回も公演があった会場 → 同上。**調べ直さない**
- 初出の会場 → 公演ページ／会場ページを開いている**そのついで**に1回だけ拾い、**1行だけ書けばよい**

**同じ箱の情報を公演の数だけ調べ直すのは、このタスクで最も起きやすい浪費である**（ツアーは同じ会場が何度も出てくる）。

**「たぶんあるだろう」という推測では書かない。** 公式サイトにアクセス情報が無い、または確認できなかった場合は、両方とも空欄のままにする。空欄の行は「くわしく」にこの2項目が出ないだけで、表示は壊れない（第3.5節の欠損耐性）。

## フェスの日割りラインナップ（`data/lineups.csv`）

フェスは1公演＝1行なので、`artists` 列には主要8組しか入らない。それだけだとカードは

> 出演：相川七瀬・新しい学校のリーダーズ・AKB48・きゃりーぱみゅぱみゅ　ほか155組

にしかならず、利用者が知りたい「**自分の好きなアーティストは何日目に出るのか**」に
1文字も答えられない。そこで全出演者を日ごとに `data/lineups.csv` へ書き出す
（設計書 第12.12節）。ここに書いた名前は**検索の索引にも入る**ので、
`artists` に入らなかったアーティストの名前でもそのフェスが見つかるようになる。

### 対象

`live_type: fes` の行のうち、**公式サイトが出演者一覧を出しているもの**。
共演（`event`）や単独公演には要らない（`artists` 列で足りる）。

### 毎回、全フェスで「取得を試みたか」を確認する

日割り取得は検証で強制されない任意工程のため、確認せず省略すると誰にも気づかれないまま
定着する。そのため `live_type: fes` の行を1件ずつ棚卸しし、`lineup_id` の有無に関わらず今週取得を
試みたかを確認する（「品質チェック」節の「フェスの日割りラインナップ」の必須項目。
ステップ2で名簿のフェスを開くついでに確認すると二度手間にならない）。

試みて読めなかった（画像/JS配信のみ、robots.txtが公式サイト全体を拒否、等）場合は
`lineup_id` を空欄のまま進めてよい——「読めないものは書かない」の原則は変わらない。
変わるのは、確認せず静かに省略することを許さない点だけである。**前回「取得不可」と
判定したフェスも、公式サイトが刷新されて日割りページが新設されている場合があるため、
`lineup_id` が空欄の `fes` 行は毎回再確認する。**

### 手順

1. その公演の `lives.csv` 側の `lineup_id` を決める（例：`luckyfes-2026`）。
   **前回すでに付けた値があるならそれを使う**（`_carry` で自動的に持ち越される）
2. `python3 tools/append_lineup.py --init` で `lineups.csv` をヘッダーだけにする
3. フェス1本ぶんずつ、公式の並び順のまま流し込む

```bash
python3 tools/append_lineup.py <<'EOF'
{"lineup_id":"luckyfes-2026","date":"2026-08-08","stage":"RAINBOW STAGE","artist":"TUBE","is_headliner":"1"}
{"lineup_id":"luckyfes-2026","date":"2026-08-08","stage":"RAINBOW STAGE","artist":"影山ヒロノブ"}
{"lineup_id":"luckyfes-2026","date":"2026-08-08","stage":"WING STAGE","artist":"NEWS"}
EOF
```

`lives.csv` が参照していない `lineup_id` を渡すと、このツールはその場で落ちる。
**表示されない行を静かに書き込むより、書く前に止めるほうがよい**ためである。

| 列                | 規則                                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lineup_id`       | `lives.csv` 側と同じ値                                                                                                                                        |
| `date`            | `YYYY-MM-DD`。**公演の会期の中の日付**（外れると `validate_data.py` がERROR）。日割りが未発表なら**空欄**。空欄の行は「日割り未発表」としてまとめて表示される |
| `stage`           | ステージ名。ステージ割りが未発表なら空欄でよい（その日の直下に並ぶ）                                                                                          |
| `artist`          | 出演者名。公式の表記をそのまま使う                                                                                                                            |
| `is_headliner`    | その日のトリだけ `1`。**公式の並びから明らかに読み取れるときだけ**（メインステージの最終枠、または最上位表記）。分からなければ空欄                            |
| `apple_music_url` | **手で書かない。** 書き終えたあとに `tools/fill_apple_music.py` が一括で埋める（後述）。絞り込めなかった名前は空欄のまま残るのが正しい                        |
| `note`            | `Opening Act` `ROJack` `深夜公演・別チケット` など、その枠の性質を一言で                                                                                      |

### 並び順を崩さない

**CSVの行順が、そのまま画面での並び順になる。** 公式が出している並び
（トリが先頭、以下出演順／主催者が決めた序列）を保つこと。
五十音順やアルファベット順に直すと、その序列の情報が消える。

### 公式ページからの取り出し方（実測）

`WebFetch` はHTMLをmarkdown化してから渡すため、一覧の構造が失われやすい。
**`curl` で生HTMLを取り、機械的に抜くほうが確実で、しかも検索の予算を一切消費しない**
（`docs/skill-feedback.md` のポスター収集と同じ手口）。実際に効いた形：

| 形                           | 取り出し方                                                                                               | 例                            |
| ---------------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------- |
| Next.js の `__NEXT_DATA__`   | `<script id="__NEXT_DATA__">` のJSONに公式タイムテーブルが丸ごと入っている（日・ステージ・出演者・時刻） | LuckyFes                      |
| 専用のJSON API               | ページのJSから `fetch()` 先を探す（`/api/get/artist/` 等）                                               | ROCK IN JAPAN FESTIVAL        |
| 日ごとの静的ページ           | `.../lineup/tokyo-day1/` のように日ごとにURLが分かれている                                               | SUMMER SONIC                  |
| 一覧に日のクラスが付いている | `data-category="day1 day2"` / `.firstday` `.secondday`                                                   | New Acoustic Camp・氣志團万博 |

**フェス公式サイトも robots.txt の判定を通る。** `check_robots.py` は
`data/sources.json` の固定名簿しか見ないが、`data/festivals.csv` のURLは
`python3 tools/fetch_gate.py --roster festivals` でまとめて確認でき、
ラインナップページを個別に開くときは取得の直前にフックが自動で判定する。

### 読めないものは書かない

ラインナップを**画像とJavaScriptでしか出していない公式サイトがある**
（2026年時点の ULTRA JAPAN がこれ）。この場合は**行を1件も作らず、`lineup_id` も空欄にする**。
他所のまとめ記事の要約で埋めると、出演しないアーティストを載せる事故に直結する。

## Apple Music アーティストリンク（`apple_music_url`）

「くわしく」の中に、**その公演のメインアーティスト1組**の Apple Music アーティストページへのリンクを出す。単独公演では出演者本人、フェス・共演では`artists`列の最初に置いた（＝最も大きく扱われる）アーティストを対象とする。全出演者ぶんのリンクは持たない。

### URLの規則性（調査結果）

Apple Music のアーティストページは `https://music.apple.com/{ストアフロント}/artist/{スラッグ}/{アーティストID}` という決まった形を取る（例：`https://music.apple.com/jp/artist/yonezu-kenshi/1051352583`）。`{アーティストID}` は名前から直接は導出できないが、**iTunes Search API（Apple公式・無認証で使える検索API）で名前から引ける**ため、機械的にリンクを組み立てられる。

```
https://itunes.apple.com/search?term={アーティスト名（URLエンコード）}&entity=musicArtist&country=jp&limit=5
```

レスポンス中の `results[].artistLinkUrl` が、そのまま正しい形のアーティストページURLになっている。`country=jp` を付けるのは、ダッシュボードの利用者が日本のストアフロント（`music.apple.com/jp/...`）を期待するため。

### 書き方の規則

1. `results` の `artistName` が調べたい名前と完全一致し、`primaryGenreName` がそのアーティストのジャンルと矛盾しない候補を選ぶ。**同姓同名・類似名の別アーティストと取り違えないこと**。確信が持てなければ書かない
2. Apple Music にページが無いアーティスト（配信を行っていない等）は空欄にする。**存在しないページへのリンクを作らない**
3. `artistLinkUrl` はそのまま使う。末尾に付くことがあるトラッキング用のクエリ文字列（`?uo=4` など）は取り除いてよい
4. `apple_music_url` は `https://music.apple.com/` から始まり `/artist/` を含むURLであること（`validate_data.py` がこの形を検証し、外れているとERRORになる）

### ラインナップ側（`lineups.csv`）は、モデルではなくツールが埋める

`lineups.csv` には数百組が並ぶ。**この列を1件ずつ手で引いてはいけない。**
名前からURLへの写像は判断を要さない決定論的な処理なので、専用のツールに任せる。

```bash
python3 tools/append_lineup.py ...   # 先にラインナップを書き終える
python3 tools/fill_apple_music.py    # そのうえで、この1コマンド
```

- **`append_lineup.py` を流し終えたあとに実行する**（CSVに無い名前は引きようがない）
- 結果は `data/apple-music.json` に残り、**2週目以降は新しく出てきた名前だけを引く**。
  数百件を毎週引き直すことにはならない
- 候補が1件に絞れない名前（`HANA` `yama` のような同名の別アーティスト）は
  **空欄のまま残る**。これは正しい挙動で、埋めようとして手で選んではいけない
- 検索URL（`music.apple.com/jp/search?...`）を**CSVに書いてはいけない**。
  `validate_data.py` が `/artist/` を含まないURLをERRORで弾く。名前から機械的に作れるものを
  データに持つと、アーティスト名を直したときにURLだけ古い名前のまま残る

> **アーティスト名は、公式の表記どおりに写すこと。** 公式サイトの見出しが大文字で
> 組まれていても、原名が小文字なら小文字で書く（`keshi` を `KESHI` と書かない）。
> 表示がそのまま変わるうえ、`fill_apple_music.py` の照合精度も落ちる。

`lives.csv` 側（各公演のメインアーティスト1組）は、これまでどおり収集の流れの中で
APIを1回叩いて確かめる。こちらはツールの対象外である。

### 実行環境の前提

`itunes.apple.com` に届かない場合（ネットワークポリシー、または `fetch_gate.py` の
拒否）は、この工程を実行できない。その場合は**`apple_music_url` を空欄のままにし、
報告にその旨を書く**こと。`fill_apple_music.py` は届かなければそこで止まり、
それまでの結果を保存して終了する（収集全体は止めない）。

空欄が多いことは品質の問題ではない——存在確認をしていないリンクを1件載せることの方が、はるかに深刻な品質問題である（「価格・クーポン記載の絶対規則」と同じ考え方）。

> **なぜ `itunes.apple.com` を開けるのか。** このホストの robots.txt は `/search*` を
> `Disallow` しているが、`fetch_gate.py` は**文書化された公開API**として例外に
> 登録している。判断の根拠と、例外を広げるときの条件は
> `docs/COLLECTION-PROTOCOL.md` 6.5.7 にある。**ここを読まずに例外を増やさないこと。**

## `desc` の書き方

100〜150字程度で、**その公演が何なのかを具体的に**書く。

### 悪い例（一般論・中身なし）

> ❌ 人気アーティストのライブです。ファン必見の公演となっています。
> ❌ 夏の野外フェス。豪華アーティストが出演します。

### 良い例（内容が具体的）

> ✅ デビュー20周年を締めくくる全国ツアーの東京ファイナル。過去のシングル曲を中心にしたセットリストで、この日限りのゲスト出演も告知されている。全席指定。
> ✅ 3ステージ制の都市型フェス。ヘッドライナー2組を含む計28組が出演し、food areaは入場券なしでも利用できる。雨天決行・荒天中止。

### 含めるべき要素

- **公演の位置づけ**（何周年ツアー／アルバムリリースツアー／ツアーファイナル／解散前の最終公演／初の単独公演 など）
- **フェスなら規模**（出演組数・ステージ数・ヘッドライナー）
- **対バン公演なら相手**
- **知らないと困ること**（全席指定かオールスタンディングか、年齢制限、雨天時の扱い）

### 含めないもの

- 主催者の宣伝文句をそのまま転記したもの
- 「必見」「感動」といった評価語
- 出典サイトの文章のコピー（**必ず自分の言葉で書き直す。著作権に配慮**）
