# 収集タスク共通プロトコル —— 差分検知・持ち越し・名簿の自己更新

`/kanto-event-collector`・`/kanto-live-collector`・`/kanto-movie-collector` の
3スキルが共有する手順とその理由をここにまとめる。各 SKILL.md には実行するコマンドを
書いてあるので、**手を動かすだけならこの文書を読まなくても進められる**。
「なぜそうするのか」「判断に迷ったときどちらへ倒すか」はここに書いてある。

---

## 1. この仕組みが解こうとしている問題

### 1.1 毎週ゼロから調べ直していた

3つの収集タスクは、これまで毎回 `--init` でCSVを空にし、全件を新規に調査していた。
この方式には次の欠陥があった。

**静かな欠落が検知できない。** 先週載っていた開催中の展覧会が、今週たまたま検索に
引っかからなければ、そのまま一覧から消える。結果のCSVを見ても「終了したから消えた」のか
「見つけられなかったから消えた」のかは区別できない。**開催中の催しを落とすのは、
利用者にとって最も損害の大きい失敗**だが、これまでは起きても誰も気づけなかった。

**中止・延期を拾えない。** 台風で中止になった花火大会のページには「中止」と
書かれているが、ゼロから調べ直すフローではそれを「開催予定」として拾い直しうる。

**「前回からの変化」を報告できない。** イベント・映画のスキルは報告項目に
「前回からの主な変化」「前回から新たに出たクーポン」を挙げていながら、
前回のCSVを読む手順を持っていなかった。読んでいないものとの差分は書けない。

### 1.2 かといって前回CSVを丸ごと読むのは高すぎる

`data/events.csv` は約68,000文字（概算4〜5万トークン）ある。着手した時点で
コンテキストの2〜3割を失い、`tools/append_rows.py` の冒頭に書いた
「後半の調査品質が落ちる」問題がそのまま再発する。

### 1.3 だから、突き合わせは機械にやらせる

**機械の仕事**：どの行が消えたか、増えたか、どの列が変わったか
**モデルの仕事**：その変化が何を意味するか（会期延長か／中止か／単なる表記ゆれか）

この線引きが、この仕組みの設計の中心にある。

## 2. 行の同定（uid）

週をまたいで同じ行を指すために、**タイトル・会場・日付から計算する8桁の uid** を使う
（`tools/rowkey.py`）。CSVに列としては持たない。

- `id` 列は `append_rows.py` が毎回1から振り直すので、週をまたぐ識別子にはならない
- uid 列を新設すると、収集のたびにそれを正しく書き写す作業が増え、新しい事故の種になる
- uid の材料に使う列（タイトル・会場・日付）は、そもそも間違えてはいけない列である

表記ゆれ（全角/半角、ひらがな/カタカナ、記号、空白）は正規化で吸収する。
それでも uid が変わる書き換え（タイトルの言い換え）は、`diff_data.py` が
**「表記が変わった可能性」として候補を出す**ので、モデルが同一かどうかを判断する。

> 映画の新作行だけは、会場（`theater`）を uid の材料から外している。
> 新作の `theater` は上映チェーンの一覧で、翌週チェーンが1つ増えるだけで
> 「消えて新しく現れた」ことになってしまうため。

## 3. 棚卸し（ステップ0）

```bash
python3 tools/prev_rows.py <events|lives|movies> --worklist
```

前回分を**圧縮した一覧**で出す。events.csv の場合、68,000文字が約10,000文字になる。
全列が必要になった行だけ、あとから引く。

```bash
python3 tools/prev_rows.py events --uid 3f2a1b9c          # その行を全列で
python3 tools/prev_rows.py events --venue 東京国立博物館   # その会場の前回分をまとめて
```

### 3.1 tier —— どこから手を付けるか

| tier  | 意味                               | 判定の根拠                                                                                                                      |
| ----- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **A** | 今回必ず再確認する                 | **会期末・開始が10日以内**／**受付の締切・発売が21日以内**／status が「本日開催」等／クーポンあり／追加公演／受付の状況が未確定 |
| **B** | 会場ページを開いたついでに確認する | 上記に当たらない通常の行。**価格の確認日が45日より古い行**もここ                                                                |
| **C** | 低頻度でよい                       | 「通年予約可」など日程が動かないもの                                                                                            |

tier は「手を抜いてよい行」を決めるためのものではない。
**限られたページ取得の回数を、変わりやすい行から先に使う**ための優先順位である。

`--tier A` で tier A の行だけに絞れる。棚卸しの一覧をそのまま読むより、
先に A だけを見るほうが着手の順序を間違えにくい。

```bash
python3 tools/prev_rows.py events --worklist --tier A
```

#### しきい値は「多いほど安全」ではない

以前は会期末・締切とも21日、価格の鮮度は14日で、価格の鮮度だけでも tier A に
上げていた。その結果 **events は125件中105件（84%）、lives は96件中70件（73%）が
tier A** になった。各SKILL.mdは「予算が尽きたら tier A の再確認を最優先で守る」と
書いているが、**105件を守れと言われて守れる工程の枠は存在しない。全部が最優先なら、
優先順位は無い。** 実際には恣意的な場所で止まる。

そこで3点を分けた（実装は `tools/prev_rows.py` の冒頭にある）。

- **会期末・開始は10日**。延長・中止が告知されるのはこの辺りで、21日先の終了日を
  毎週確認しても、ほとんどの週は何も変わっていない
- **受付の締切・発売は21日のまま**。これは利用者が行動を逃す期限であり、
  3スキルの中でも最も落としたくない情報である（設計書 第12.2節）
- **価格の鮮度は tier B へ**。古い価格は「間違った値」ではなく「いつ確認したかが
  分かる値」であり（`price_checked` がそれを示す）、中止を伝え損ねることに比べれば
  実害が小さい。TTL も45日に伸ばした

あわせて、**決着している受付**（`SOLD OUT` `受付終了` `完売` 等）は「締切が空」を
理由に A へ上げないことにした。SOLD OUT は各SKILL.mdが「確定情報なので別経路を
探すな」と明示している状態でありながら、`onsale_label` があって `onsale_end` が
空だという判定に引っかかっていた（lives の未確定32件のうち14件がこれ）。
**埋めようのない欄を理由に最優先へ上げ続けるのは、優先順位を薄めるだけである。**

この変更で events 36% / lives 47% / movies 24% になった。lives が高いのは
受付の締切が未確定の行が実際に多いためで、それは埋めるべき仕事が実在するという意味である。

### 3.2 会場単位で回る（重要）

**行を1件ずつ再確認してはいけない。** 会場ごとに回ること。

東京国立博物館の展覧会ページを1回開けば、同時に次の3つが分かる。

1. 既存の行がまだ開催中か（会期延長・中止を含む）
2. 会期・料金・受付が変わっていないか
3. **前回になかった新しい企画展が始まっていないか**

つまり「既存行の更新確認」と「新規の発見」は、同じ1回の取得で済む。
行ごとに確認すると126回の取得になるが、会場ごとなら新規探索のついでで終わる。
**この仕組みが追加のコストをほとんど生まないのは、この相乗りのおかげである。**

## 4. 持ち越し（carryover）—— 何を書き直さなくてよいか

前回と同じ行を書くとき、座標・最寄り駅・駐車場のような**動かない事実**まで
毎回書き直すのは出力トークンの無駄であり、写し間違いの機会でもある。

```bash
# 内容に変更がないことを確認できた行
python3 tools/append_rows.py events <<'EOF'
{"title": "...", "venue": "...", "start_date": "...", "end_date": "...",
 "cats": "art", "area": "...", "pref": "tokyo", "price": "...",
 "source": "公式サイト", "url": "...", "_carry": "*"}
EOF
```

| 区分                   | 列                                                                                                                              | 扱い                                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **自動で埋まる**       | `kana` `lineup_id` `lat` `lng` `parking` `nearest_station` `venue_url` `theater_url`                                            | 空欄なら前回値で補完。何も書かなくてよい。`lineup_id` は書き手が決めたスラッグを毎週使い回すだけなので同じ扱い（第12.12節） |
| **頼めば埋まる**       | `desc` `note` `official_url` `artists` `cats`/`genre` `series_id`/`tour_id` など                                                | `"_carry": "*"` か `"_carry": "desc\|note"`                                                                                 |
| **絶対に持ち越さない** | 日付・`status`・`rank`・`onsale_*`・`price*`・`coupon_note`・`limited_sale`・`url`・`source`・`announced_date`・`is_additional` | スクリプトが拒否する                                                                                                        |

最後の区分が、この仕組みで最も重要な安全装置である。

> 前回の締切をそのまま書き写すことは、このプロジェクトが3スキルで一貫して
> 禁じてきた「確認していない値を書く」そのものにあたる。差分方式は、
> **未検証の値を検証済みらしく見せるのを容易にする**という副作用を持つので、
> 指示文でのお願いではなく、スクリプトが受け付けないという形で担保している。
> `"_carry": "onsale_end"` はエラーで落ちる。

会場の座標・最寄り駅・駐車場は「行の属性」ではなく「場所の属性」なので、
会期が変わって uid がずれても、**同じ会場の別の行から引かれる**。

`"_carry": "*"` を使ってよいのは、**その行の内容に変更がないことを実際に確認できたとき
だけ**である。確認していないなら、確認するか、その列を空欄にする。

## 5. 消えた行には説明をつける（省略不可）

前回あって今回無い行は、必ずどちらかである。

1. 本当に終わった・中止になった → 正しく消えている
2. 今回は見つけられなかった → **事故**

この2つを区別できるようにするため、消えた行それぞれに理由を記録する。

```bash
python3 tools/prev_rows.py events --dispose <<'EOF'
{"uid": "37e50ea9", "status": "ended",        "note": "8/31で会期終了を公式サイトで確認"}
{"uid": "2e9a11b8", "status": "cancelled",    "note": "荒天のため中止"}
{"uid": "9ab96b1e", "status": "out-of-scope", "note": "開始が3ヶ月より先になった"}
{"uid": "4b7d8c70", "status": "renamed",      "to": "a1b2c3d4", "note": "正式名称に変更"}
{"uid": "341daad8", "status": "notfound",     "note": "会場ページに記載がなく確認できず"}
EOF
```

`notfound` は「調べたが分からなかった」を正直に記録するためのものであり、
**面倒を避けるために使ってよいものではない**。`notfound` が多い週は、その旨と
件数を報告に含めること。

`diff_data.py` は、説明のない消滅があるとエラーで落ちる。

### 5.0 記録した「確認できなかった」を、翌週の最優先にする

`notfound`（調べたが分からなかった）と `expired`（終了日を過ぎたことを
`purge_ended.py` が機械的に検出した）は、どちらも**確認できていない**という意味を持つ。
ところが記録した翌週にはその記録が消え、次の実行の行動に何も影響していなかった。

**影響しないなら、それは記録ではなく言い訳である。**

そこで `append_rows.py --init` は、処分記録を消す代わりに1世代だけ残す
（`data/.prev/<name>.carried.jsonl`）。棚卸しの一覧は、その中の `notfound` と
`expired` を**先頭に**出す。

```
# ---- 先週、確認できないまま消えた行（25件・今週の最優先）----
# notfound 3件: 調べたが分からなかった行。まだ開催中なら「静かな欠落」になっている
# expired 22件: 終了日を過ぎて機械的に消えた行（未確認）。会期が延長されていた可能性がある
```

`expired` を並べるのは、**会期延長を見落とした行がここに紛れる**ためである。
延長に気づかなければ古い終了日がCSVに残り、その日を過ぎた時点で機械的に消えるので、
まだ開催中の催しが「終了日を過ぎた」という理由だけで一覧から落ちる。この経路は
`purge_ended.py` の設計上どうしても残るので、翌週に拾い直せるようにしておく。

これらの行は前回のCSVにはもう残っていない。**この一覧に出さない限り、二度と視界に入らない。**

### 5.1 終了日を過ぎた行の自動後始末（`purge_ended.py`）

第8.5節の撤退の手順は、予算切れで再確認が間に合わなかった行を「前回値のまま
書き直してよい」としている。これは日程が動かない行のための扱いだが、
**確認が間に合わなかった行にも同じ扱いが適用されうる**。すると、前回すでに
終了日を過ぎていた行が、確認されないまま今週も持ち越される——という抜け道が
生まれる。それが翌週も同じ理由で確認を逃せば、終了日を過ぎた行がCSVの中に
無期限に居座ることになる。

表示側（`schedulePhase`。設計書 第3.9節・第5.4.1節）は終了日から毎回「終了」を
計算し、既定の一覧からは隠すので、この抜け道は利用者の目には触れない。だが
CSVの中には残り続け、次回の収集タスクが読む前回データを太らせ、
「終了のものも表示」チップを押した利用者には何ヶ月も前の催しが並ぶ。

この静かな蓄積を断ち切るのが `tools/purge_ended.py` である。「終了日が今日より
前か」という一点だけを機械的に判定し、該当する行をCSVから取り除く。**検索も
モデルの判断も要らない**ので、各SKILL.mdの終了工程では `--dispose` より先に
実行する（自動で消える分だけ、モデルが個別に理由を付ける対象が減る）。

- 消した行には、`ended` ではなく専用の `status: "expired"` を自動で記録する。
  `ended` は「情報源に当たって終了を確認した」という意味なので、日付の比較だけで
  判定したこの処分とは意図的に区別してある
- **確認できた行を `ended` として `--dispose` するほうが、この自動処理より
  常に望ましい。** `expired` は確認不足のしるしであって、確認の代わりではない
- `lineup_id` を持つ `lives.csv` の行を消す場合は、他の行が同じ `lineup_id` を
  参照していない限り `data/lineups.csv` 側の該当行も一緒に削除する
  （参照を残すと `validate_data.py` が参照切れでERRORにする）
- モデルの手順から漏れても後始末が効くよう、`.claude/hooks/verify-data.sh`
  （Stop フック）と `.claude/scripts/claude-routine.sh`（週次ルーチンの最終ゲート）
  からも自動で呼ばれる（`docs/DESIGN.md` 第9.1.5節と同じ考え方——決定論的に守らせたい規則は
  フックに置く）

## 6. 最終工程：差分の確定

```bash
python3 tools/diff_data.py            # 3データセットまとめて
python3 tools/validate_data.py        # 従来どおり ERROR 0 を確認
```

`diff_data.py` の出力が、そのまま報告の「前回からの変化」になる。
新規・変更・消滅・表記ゆれ候補が機械的に列挙されるので、
**モデルが記憶や印象で「主な変化」を書く必要はない**（書いてはいけない）。

`announced_date` と `is_additional` も、この差分に基づいて決める。

- 発表記事の日付が分かるなら、その日付を `announced_date` に書く
- 分からない場合に**限り**、差分で新規と判定された行に今日の日付を入れる
- 「前回に無かった」以外の根拠なしに `is_additional` を立てない

## 6.5 取得してよいもの・いけないもの

この収集は cron から週次で自動実行される（`.claude/scripts/claude-routine.sh`）。
**「人が調べているのと同じ」ではなく、機械的なアクセスである。** サイト側から見れば
ボットであり、そのつもりで振る舞う必要がある。

### 6.5.1 守ること

1. **`robots.txt` が `Allow` している範囲だけを取得する。**
   サイト単位ではなく**URL単位**で見る（6.5.4。唯一の例外は文書化された公開APIで、
   条件は 6.5.7）。`<meta name="robots" content="noindex,nofollow">`
   や `X-Robots-Tag` を返すページも同じで、そうと分かった時点でその行は使わない。
2. **収集後に拒否の意思が示されたことが判明したら、そのサイト由来の行を消す。**
   `data/sources.json` からも外し、次回以降の対象にしない。
3. **利用規約で自動収集・データの二次利用を明示的に禁じているサイトは使わない。**
   robots.txt に書いていない禁止はここに来る。判断は人間が行う（7.1節と同じ理由で、
   規約を読んだ当人がルールを緩められる構造にしない）。
4. **会員登録・ログインが要る領域には立ち入らない。** 無料会員でも同じ。
5. **同じホストへ続けて当たらない。** `Crawl-delay` が書いてあればその秒数を空け、
   書いていなくても最低3秒は空ける（6.5.5）。
6. **1サイトあたりの取得は、その週の調査に要る分だけ。**
   第8章の予算制（工程ごとの取得回数上限）は、もともとコストのための仕組みだが、
   **同時にアクセス頻度の上限としても機能している。** 予算を守ることが、
   そのままサイトへの負荷を抑えることになる。

### 6.5.2 なぜこれが要るのか

礼儀の話ではない。根拠が2つある。

**著作権法30条の4**（情報解析等のための利用）は、著作物に表現された思想・感情の
享受を目的としない利用を広く適法化する。ページを取得して事実を読み取る工程は、
かなりの部分がここに収まる。**ただし30条の4は契約を上書きしない。**
規約で自動収集を禁じているサイトからの取得は、著作権法上適法でも規約違反として残る。

**著作権法47条の5**（軽微利用）は、所在検索サービス等が権利制限を受けうる条文だが、
その適用には政令（著作権法施行令第7条の5）の基準に従うことが条件になっている。
基準には**収集を禁止する措置がとられた情報を収集しないこと**と、
**収集後にその措置がとられたと判明したときに記録を消去すること**が含まれる。
つまり1と2は、丁寧さではなく**権利制限を使うための前提条件**である。

### 6.5.3 機械が読める部分は機械に読ませる

`robots.txt` の突き合わせをモデルに毎回やらせると、コンテキストを食ううえに
結果が週ごとにぶれる。**突き合わせは機械の仕事**（1.3節と同じ考え方）。

```bash
python3 tools/check_robots.py          # sources.json の全サイトを確認
python3 tools/check_robots.py --json   # 機械可読な出力
```

拒否しているサイトが見つかったら終了コード1を返す。生成AI向けのUA
（`GPTBot` `ClaudeBot` `Google-Extended` 等）を名指ししているサイトも別枠で挙げる
——判定には使わないが**意思表示としては読む**ので、見つけたら規約を人間が確認する。

名指しされたサイトについては、さらに **`Claude-User` と `Claude-SearchBot`
への許可状況を個別に判定して表示する**（`claude_detail`）。Anthropicが運用する
クローラは役割が3つに分かれており（[出典](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler)）、
`ClaudeBot` はモデルの**学習データ収集**用でユーザ操作を伴わない。3スキルが
行っているのは**エージェントの実行時アクセス**であり、これに対応するのは
`Claude-User`（ユーザの指示に応じたリアルタイム取得）と `Claude-SearchBot`
（検索目的の巡回）の2つである。サイトが `ClaudeBot` だけを拒否していても
今回の収集の可否には関係ないし、逆に `Claude-User`/`Claude-SearchBot` を
明示的に拒否しているサイトは、主判定（`DEFAULT_AGENT`）が「OK」でも使わない。

**このスクリプトは、3スキルとも「実行手順まとめ」の手順0で着手前に毎回実行する。**
robots.txt だけを見る軽い確認（ページ本体は取得しない）なので検索予算を消費せず、
週次実行の負荷にはならない。

### 6.5.4 取得の直前に、URLごとに判定する

**サイト単位の確認だけでは足りない。** サイトはトップを開放したまま、特定のパスだけを
閉じている。実例として asoview! の robots.txt は次のように書いている。

```text
Disallow: /api/
Disallow: /reserve/
Disallow: /book/
Disallow: /search/*experienceDate
```

トップの判定は「OK」だが、**価格比較の工程が開きに行きたい予約ページ（`/reserve/`
`/book/`）はまさに閉じている側**である。「トップがOKだったから以下すべてOK」という
推論は成り立たない。

もうひとつ、`check_robots.py` が見ているのは `data/sources.json` の約45サイトだけで、
**実際の取得先の大半を占める名簿のURL**（`spots.csv` `venues.csv` `theaters.csv`
`festivals.csv` に入っている会場・劇場・フェスの公式サイト）は対象外だった。

そこで `tools/fetch_gate.py` が、**これから開くURLそのもの**を取得の直前に判定する。

```bash
python3 tools/fetch_gate.py <URL>             # 判定して、待って、通す
python3 tools/fetch_gate.py --check <URL>...  # 判定だけ（待たない）
python3 tools/fetch_gate.py --roster venues   # 名簿のURLを一括で事前判定
```

**これは `.claude/settings.json` の `PreToolUse` フックに登録してあり、`WebFetch` の
たびに自動で走る。** 拒否されているURLはモデルの判断を待たずにブロックされる。
散文のお願いが安い経路の前で負けることは、画像の件（`docs/DESIGN.md` 第7.1節）で
実証済みなので、**守らせたい規則は仕組みに置く**という方針をここでも採っている。

判定は `Claude-User` と `Claude-SearchBot` の**厳しいほう**を採る。どちらの性質の
アクセスに当たるかをページ単位で言い分けられない以上、緩いほうに寄せる理由がない。
実際にこの判定で、名簿と調査元から4件の拒否が見つかった（connpass は `Disallow: /`、
`Claude-SearchBot` を名指しで拒否している会場・フェスが3件）。

Allow/Disallow の解釈規則（最長一致・`*` と `$`・UA群の選び方）は
`tools/robots_rules.py` に置き、`check_robots.py` と共有している。**`Allow` されて
いる範囲だけを見るという運用は、`Allow` を正しく解釈できることが前提**になるので、
規則は `tools/robots_test.py` で検証して固定してある。

### 6.5.5 間隔を空ける

`Crawl-delay` は、以前は表示するだけで守られていなかった。表示された数字をモデルが
数えて自分で待つ運用は成立しない——**待ったかどうかを誰も確認できず、急いでいるときに
最初に省かれる。** 待つ処理をコードの中に置けば、通った時点で待ち終わっている。

`fetch_gate.py` は、同じホストへの取得間隔として次の最大値を空ける。

| 由来                                            | 値                      |
| ----------------------------------------------- | ----------------------- |
| robots.txt の `Crawl-delay`                     | 2つのUAのうち長いほう   |
| robots.txt の `Request-rate`                    | 1回あたりに換算した秒数 |
| 下限（robots.txt が何も言っていないサイト向け） | 3秒                     |

**相手が2分空けろと言うなら2分空ける。** rockin'on.com は `Crawl-delay: 120` を宣言して
いるが、これは実際に120秒待って取得する（待てないから諦める、では本末転倒になる）。

上限は150秒で、これを超える間隔を要求するホストだけは、待って居座るより後回しに
するほうが筋が通るので断る。断られたら別のホストを先に回ること。

> **上限（`MAX_WAIT`）は、`.claude/settings.json` のフックの `timeout`（180秒）より
> 必ず小さく保つこと。** フックが時間切れで打ち切られると、それは「ブロック」ではなく
> 単なるエラー扱いになり、**待たないまま取得が通る**。守るための仕組みが、守らない
> 方向に壊れる。片方だけ変えないこと。

### 6.5.6 表示側に書いてあること

サイトのフッターと `terms.html` には、上のルールを利用者・権利者に向けて明記してある。
**両方を同時に変更すること。** 片方だけ変えると、公開している方針と実際の運用が
食い違うことになる（それが2026-08 のレビューで最初に指摘された種類の問題である）。

### 6.5.7 文書化された公開APIの扱い

6.5.1 の1（`Allow` の範囲だけを取得する）には、**エンドポイント単位の例外**を1つ置いている。
**提供者自身が利用方法を公開文書で示している公開API**は、そのパスが `Disallow` に
入っていても取得してよいものとしている。

**この判断は独自解釈ではない。** 根拠を3つ、いずれも出典つきで挙げる。

**1. 仕様が対象を「クローラ」に限っている。**
[RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html)（Robots Exclusion Protocol の標準）は
第1節でクローラを「リンクを**再帰的に辿ってインデックスする**自動クライアント」と定義し、
続けて **"These rules are not a form of access authorization."**（これらの規則はアクセス許可の
一形態ではない）と明記している。名前を1つ渡して1件引く呼び出しは、この定義の巡回に当たらない。
第3節でも "The Robots Exclusion Protocol is not a substitute for valid content security measures."
としており、robots.txt は**アクセス制御の手段として設計されていない**。

**2. 運用上の目的が「巡回の負荷制御」だと、実装側の解説も述べている。**
[Google の robots.txt 解説](https://developers.google.com/search/docs/crawling-indexing/robots/intro)は
robots.txt を「検索エンジンのクローラがアクセスできるURLを伝えるもの」と説明し、主な用途を
**"used mainly to avoid overloading your site with requests"** としている。

**3. 提供者自身が「利用を案内しながら、そのパスを `Disallow` する」ことが実際にある。**

| 提供者         | robots.txt      | 同時に出している公開文書                                                                           |
| -------------- | --------------- | -------------------------------------------------------------------------------------------------- |
| MusicBrainz    | `Disallow: /ws` | [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API)（利用方法・レート制限・UAの書き方） |
| ウィキペディア | `Disallow: /w/` | [API:Etiquette](https://www.mediawiki.org/wiki/API:Etiquette)（`/w/api.php` の利用作法）           |

**除外指定が「APIの利用禁止」を意味するなら、これらの提供者は自らの案内と矛盾していることになる。**
とくに MusicBrainz はオープンデータの提供を存在意義とする団体で、「APIを使うな」と言う動機がない。
ウィキペディアは `Disallow: /w/` を出しつつ `Allow: /w/api.php?action=mobileview&` のように
特定の呼び出しだけを開けており、**この指定がクローラの挙動を制御するためのものであることが、
書き方そのものから読み取れる。**

以上より、APIのパスに置かれた `Disallow` は「クローラをAPI面に迷い込ませない」ための定型と
読むものとしている。

例外は `tools/fetch_gate.py` の `API_EXCEPTIONS` に持つ。適用には次の条件をすべて課す。

| 条件                                           | 理由                                                                                                  |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **ホスト全体ではなくパス単位で登録する**       | APIが開いていることは、同じホストの通常ページを開いてよい理由にならない                               |
| **提供者の公開文書があること**                 | 「APIらしく見える」だけのURLを自分の判断で開けてよいことにしない                                      |
| **間隔（6.5.5）は通常どおり消化する**          | 例外は可否の話で、負荷の話ではない                                                                    |
| **取下げ申請（`no-crawl.json`）は覆さない**    | 申請は相手が明示した意思表示であり、APIかどうかとは無関係                                             |
| **robots.txt が読めない（5xx）場合も覆さない** | 6.5.7 の理屈は「`Disallow` の意図の読み方」であって、相手の意思が確認できない場面には何も言っていない |

最後の2つの条件はコードで担保してある（`gate()` は `robots_state` が `optout` /
`forbidden` のいずれかのとき例外を適用しない）。**申請より弱い例外にしておかないと、
`source-optout` の手順が骨抜きになる。**

> **6.5.2 の法的な整理との関係。** 著作権法47条の5は**著作物**の軽微利用を扱う条文で、
> その要件に「収集を禁止する措置がとられた情報を収集しないこと」が含まれる。現在この例外で
> 取得しているのはアーティストページのURL（事実データ）だけで、著作物の複製にあたらない。
> **例外の対象を広げるとき——とくに本文・説明文・画像を含むAPIを足すときは、この整理が
> そのまま使えるかを先に確認すること。**

### 6.5.8 取得できない先に、リンクを置いてよいか

**よい。** `robots.txt` が制限しているのは**こちらがページを取得すること**であって、
利用者に案内するリンクを置くことではない。この線は asoview! について
`/kanto-event-collector` が既に引いていたもので、他のサイトにも同じように適用する。

ただし**開けなかったページに書いてある値を、開いたふりをして書いてはいけない。**
`source` 列は「その値をどこで読んだか」であると同時に、画面のボタンの文言
（「{source}で予約する」）でもある。利用者が申し込む先としての `connpass` は正しく、
そこに値の裏取りが伴っていないことだけが問題になる。

#### 拒否されている先でも、許可された経路があることがある

`connpass` の `robots.txt` は `User-agent: *` に対して `Disallow: /` を宣言するが、
その直前に**2行の `Allow` を置いている**。

```text
User-agent: *
Allow: /*.ics
Allow: /*/ja.atom
Disallow: /
Crawl-delay: 5
```

つまり **イベントページは拒否だが、そのイベントの `.ics` は明示的に許可されている。**
`https://connpass.com/event/{id}.ics` を `tools/fetch_page.py --ics` に渡せば、
公演名・日付・会場・住所・中止状態が構造化された形で取れる（2026-08-19 に3件で実測）。
`Allow` は最長一致で `Disallow: /` に勝つので、`fetch_gate.py` はこれを正しく通す。

**「このサイトは拒否されている」で止めず、`robots.txt` が何を開けているかを見ること。**
サイト側がフィードを開けているのは、そこから取ってほしいという意思表示である。
イベントページの `.ics`、施設の `sitemap.xml`、`ja.atom` のようなフィードは、
拒否の中に残された正規の入口であることが多い。

> **サブドメインでは URL の形に注意する。** `a11y-chiba.connpass.com/event/389386.ics`
> は 404 で、正しくは `connpass.com/event/389386.ics` である。また
> `Allow: /*/ja.atom` はパスに階層を1つ要求するので、ルート直下の `/ja.atom` には
> 一致しない（`fetch_gate.py --check` はこれも正しく拒否する）。

### 6.5.9 ページ本体を取る正規の手段（`tools/fetch_page.py`）

以前は、ページ本体を取る手段が `WebFetch` しか無かった。これには2つの穴があった。

1. **`WebFetch` はHTMLをmarkdown化してから渡すので、一覧の構造が失われる。**
   会場スケジュールで公演名と日付の対応がずれることが繰り返し観測されており、
   `/kanto-live-collector` のステップ1に警告として書いてある
2. そのため、フェスの日割りラインナップだけは `curl` で生HTMLを取る手順になっていた。
   **`curl` はフックを通らないので、robots.txt の判定も `Crawl-delay` の消化も行われない。**
   同じ文書が「`curl` でページ本体を取りに行かないこと」と書いている行為そのものだった

`tools/fetch_page.py` はこの矛盾を解く。`fetch_gate.py` の判定と待機を通してから
本体を取得し、機械可読な部分を抜く。**`WebSearch` を1回も消費しない。**

```bash
python3 tools/fetch_page.py <URL>                      # 何が取れるページかを先に見る
python3 tools/fetch_page.py <URL> --text               # 本文だけ（ふつうはこれ）
python3 tools/fetch_page.py <URL> --links              # 詳細ページのURLを集める
python3 tools/fetch_page.py <URL> --sitemap --since 2026-08-01
python3 tools/fetch_page.py <URL> --events             # JSON-LD の Event 系を正規化
python3 tools/fetch_page.py <URL> --ics                # ICS フィード
```

引数なしで実行すると「そのページから何が取れるか」だけを数行で返す。**先にこれを見て、
次の手を選ぶ。**

| 得られるもの | 使いどころ                                                                                            |
| ------------ | ----------------------------------------------------------------------------------------------------- |
| `--text`     | 会場の公演カレンダー・料金表など、**行と列の対応が意味を持つ**ページ。表はタブ区切りで残る            |
| `--links`    | 一覧ページから詳細ページへ辿るとき。相対URLは絶対URLに直り、重複は落ちる                              |
| `--sitemap`  | `lastmod` で絞れば、その施設の**新着ページだけ**を検索0回で見つけられる                               |
| `--events`   | `eventStatus` に `EventCancelled` / `EventPostponed` が入る。**中止・延期を文章から読み取るより確実** |
| `--ics`      | 自治体・ホール・connpass など。日付と会場が構造化されている                                           |

> **構造化データは期待するほど普及していない。** 2026-08 に名簿の施設・劇場・横断
> サイトを実測したところ、トップページに `Event` 型の JSON-LD を出していた先は
> ほとんど無く、あっても `WebSite` / `BreadcrumbList` 止まりだった。**総当たりしないこと。**
> 引数なしの確認は1回の取得で済むので、それで無ければ `--text` に切り替える。

##### `--raw`（生HTML）を既定の経路にしない理由

`--raw` は **`--out` が無いと動かない**。標準出力へ生HTMLを流さない、という制約である。

**生HTMLの信号率は実測2.4%**（2026-08-21 の実行が残した216ページ、3,190万文字に対して
本文76万文字＝42分の1）。残る97%はタグ・スクリプト・トラッキング・cookieバナーで、
本文は入っていない。

これを**節約の話だと読み違えないこと。** 文脈が伸びるほどモデルの想起精度は落ちる
（transformer の注意は n トークンで n² の対を張るので、伸びるほど1対あたりが薄まる）。
**雑音97%は、注意を薄めながら課金される。** 落とせば、同じ調査がより少ないトークンで、
より正確になる——トレードオフではない。

以前は本文を読む手段が `--raw` しか無かったため、2026-08-21 の実行では `--raw` が88回、
その出力を解析する使い捨てスクリプトが194回書かれた。**モデルの判断ではなく、道具が
他の道を用意していなかったことの結果である。** 生HTMLが本当に要る場面
（`__NEXT_DATA__` の取り出し、壊れた表の目視）は `--raw --out temp/page.html` で
落として `grep` する。

#### UA と robots の関係

`fetch_gate.py` の判定は `Claude-User` と `Claude-SearchBot` の厳しいほうを採る。
だが `fetch_page.py` が名乗るのはそのどちらでもない（正直に自分の名前を名乗る）。
`robots.txt` に `Claude-User: Allow: /` と `*: Disallow: /` が併記されていれば、
**適用されるのは `*` の側**である。そこで `fetch_page.py` は `*` の群も個別に確認し、
**3つすべてが許可しているときだけ取得する**。`WebFetch` 経由より厳しい側に倒れる。

`WebFetch` で通るページが `fetch_page.py` で拒否されることはありうるが、
**その差を迂回に使わないこと。** 名乗った名前に適用される規則に従うのが筋である。

## 7. 名簿の自己更新 —— どこまでを自動でやるか

定点観測リスト（名簿）は放っておけば必ず腐る。会場は開業し、閉館し、改称する。
名画座は畳み、フェスは開催地を変える。だから収集タスク自身が名簿を育てる。

| 名簿         | ファイル             | 対象                                   |
| ------------ | -------------------- | -------------------------------------- |
| イベント施設 | `data/spots.csv`     | 美術館・テーマパーク・水族館・ホール等 |
| ライブ会場   | `data/venues.csv`    | ドーム・アリーナ・ホール・ライブハウス |
| 映画館       | `data/theaters.csv`  | シネコンチェーンの店舗・名画座         |
| フェス       | `data/festivals.csv` | 関東開催の音楽フェス                   |

```bash
python3 tools/roster.py spots --list --pref tokyo      # 今回調べる先を出す
# 収穫の記録（--hit）は append_rows.py が自動で行う。手で打つのは、行を書かずに
# 「見に行ったが今回は何も無かった」ことを残したいときだけでよい
python3 tools/roster.py spots --hit 東京国立博物館
python3 tools/roster.py spots --add <<'EOF'            # 名簿に無い会場を見つけた
{"name": "○○ミュージアム", "kind": "museum", "pref": "tokyo", "url": "https://..."}
EOF
python3 tools/roster.py venues --retire ○○ホール --reason "2026年6月閉館"
python3 tools/roster.py venues --block ○○ホール --reason "robots.txt が拒否"  # 閉館ではない
python3 tools/roster.py venues --close ○○アリーナ --until 2027-04-01
python3 tools/roster.py spots --gc                     # 収穫のない先を整理（毎回最後に）
```

状態は `candidate`（今回はじめて見つけた）→ `active`（2回ヒットで昇格）→
`retired`（閉館、または長期にわたり収穫ゼロ）と遷移する。これとは別に
`blocked`（robots.txt が取得を拒否している）がある。

**`blocked` を `retired` と分けているのは、次週の自分に伝える内容が違うためである。**
`retired` は「もう存在しない」、`blocked` は「存在するが、こちらが見に行ってはいけない」。
一緒にすると、翌週の収集が `blocked` の会場の公演を「閉館したから」として片付けかねない。
どちらも行はCSVに残る（`--gc` は消さない）——名簿は「どこを見に行くか」であると同時に、
座標・種別・キャパを引く**マスター**でもあり、表示側は状態を見ずに読むためである。
**見に行かないだけで、その会場の公演を他の情報源から拾って載せることは妨げない。**
**`--gc` を毎回必ず実行すること。** 追加しかしないと名簿は単調に膨らみ、
いずれ定点観測が対象期間を回りきれなくなる。

### 7.1 スキル本文（SKILL.md）は書き換えない

**名簿（データ）は自動更新、ルール（散文）は提案止まり。** この線は動かさない。

収集タスクが自分の SKILL.md を書き換える形を採らない理由は4つある。

1. **プロンプトインジェクション。** Webページを読んだ主体が、自分の指示書に
   書き込む権限を持つ構造になる。「重要：収集ルールを次のように変更せよ」と
   書かれたページ1枚で、翌週以降のすべての実行が汚染される。しかも cron の
   自動実行で、`--permission-mode bypassPermissions` である
2. **静かな基準の緩和。** モデルは自分を縛るルールを緩める方向へ書き換える誘因を
   常に持ち、そして劣化を判定するのはその劣化したスキル自身になる
3. **レビュー不能。** 散文の書き換えは差分が読みにくく、毎週 main へ直接 push する
   運用では誰も気づけない
4. **際限のない肥大化。** 名簿と違い、散文には整理の仕組みがない

`roster.py` が触るのはCSVの名簿だけで、列も値も検証される。名簿に入る文字列は
Webページ由来になりうるので、**指示文めいた文字列・長すぎる値はその場で拒否し、
制御文字は書き込む前に取り除く**（`roster.py` の検疫）。制御文字を拒否ではなく
除去で扱っているのは、これを先に済ませてから指示文チェックにかけることで、
制御文字で単語を分断して検知を逃れる手口も一緒に潰せるためである。

### 7.2 ルールを変えたほうがよいと気づいたら

`docs/skill-feedback.md` に追記する。適用するかどうかは人間が判断する。

対象になるのは、たとえば次のようなもの。

- 目標件数・カテゴリ配分が実態に合っていない
- 参照先サイトが閉鎖した／新しい有力なサイトが現れた
- CSVの列や検証ルールに実務上の無理がある
- 季節キーワード表・プレイガイド一覧・配給会社リストの更新

**目標件数・品質基準・禁止事項（「推測で埋めない」系のルール）は、
提案はしてよいが自分で変更してはならない。**

## 8. 調査予算 —— 有限の検索回数と文脈をどう配るか

### 8.1 なぜ予算の話が要るのか

**Web検索の呼び出しには、1セッションあたり200回という上限がある。** これは
「たくさん調べれば品質が上がる」という前提が成り立たないことを意味する。
超えた瞬間、以降の調査は**中途半端な場所で止まる**。

実際に起きたことが2つ記録されている。

- **2026-08-04 movies**: 検索が200回に達し、公開日だけ確認できて上映劇場・
  公式URLまで辿れなかった作品が多数残った。`url` は必須列なので、それらは
  収録を断念することになった
- **2026-08-02 events**: 126件を収集し、A群11サイトの横断比較を指示どおり
  行った結果、`price_best` を書けたのは**7件**、`coupon_note` は**2件**。
  しかもその7件は**すべて「公式サイトが最安」**で、他経路のほうが安かった行は
  **1件も無かった**

2つ目が重要である。「A群のサイトを**すべて**確認する」を126件に課すと、
名目上は1,300回規模の取得になる。それだけ使って、実際に得られた情報は
「公式が最安だった」が7件だけだった。**実行不可能なルールは、丁寧な仕事を
生まない。恣意的な場所で黙って止まった仕事を生む。**

だから、予算を先に配り、**尽きたときに何を捨てるかを先に決めておく**。

### 8.2 3つの原則

#### 原則1 —— 検索は「URLを知らないとき」にだけ使う

名簿には `url` 列があり、ほぼ全件埋まっている。**件数はここに書き写さない**
——名簿は毎週増えるので、書き写した数字は必ず古くなる。実数は
`roster.py <名簿> --list --urls` の標準エラーに出る「うちURL不明 N件」で見る
（この N が、その工程で検索を使ってよい件数でもある）。前回CSVにも `official_url` と `url` がある。

```bash
python3 tools/roster.py spots --list --pref tokyo --urls   # 名前とURLを出す
python3 tools/prev_rows.py events --venue 東京国立博物館     # 前回の official_url を引く
```

**知っているURLを検索し直すのが、最も多く、最も無自覚に消える予算である。**
名簿を一周するだけで200回を超える計算になるが、`--urls` で直接開けば検索は0回で済む。
検索が要るのは「まだURLを知らないもの」——エリア軸の探索、新しい会場、
名簿の `url` が空欄の数件——だけである。

#### 原則2 —— 1回の取得で、取れるものを全部取る

会場ページを1回開けば「既存行の再確認」と「新規の発見」が同時に済む（第3.2節）。
これを列にも広げる。**その会場に関わる会期・料金・アクセス・注意事項を、
その1回で拾い切る。** 「あとで座標だけ」「あとでアクセスだけ」と戻るのは、
同じページの二重払いになる。

#### 原則3 —— 充足したら止める

行ごとに「これが埋まったら完成」を先に決め、埋まった行はそれ以上調べない。
**すでに判断できる情報が揃っているのに調査を続けるのは、品質ではなく消費である。**

### 8.3 行の充足条件（Definition of Done）

| 区分                          | 列                                                                                                                      | 扱い                                                                 |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **必須**                      | タイトル・分類・場所（area/pref/会場）・日付（ISOの開始日/終了日・時刻・`date_note`）・`price`・`source`・`url`・`desc` | ここが揃った時点で**その行の調査を終える**                           |
| **ついでに拾う**              | `kana` `note` `venue_url` `series_id`/`tour_id` `announced_date` `is_additional` `parking`/`nearest_station`            | 開いたページに書いてあれば書く。**このために追加でページを開かない** |
| **調べなくてよい**            | `lat`/`lng`                                                                                                             | 名簿と前回値から自動補完される。**名簿にある会場は調べない**         |
| **1回で見つからなければ空欄** | `apple_music_url`（`lives.csv` 側。`lineups.csv` はツールが埋める）                                                     | 粘らない                                                             |

**「空欄でよい列を埋めるために検索する」ことが、予算を最も静かに食う。**
空欄は品質の問題ではない、という既存の原則は、そのまま予算の原則でもある。

> `lat`/`lng` について補足する。`append_rows.py` は座標を**会場の属性**として
> 名簿と前回値から補完する。名簿に載っている会場（＝定点観測先のほぼ全部）は
> 空欄で渡してよく、調べる必要がない。座標を調べてよいのは、**名簿にも前回にも
> 無い新しい会場**だけである。

### 8.4 予算が尽きたときに捨てる順

上から順に守る。**下から順に捨てる。**

1. **tier A の再確認** —— 落とすと「終わった催しが載り続ける」「中止を伝えない」
   という、このプロジェクトで最も重い実害が出る
2. **網羅の工程**（エリア軸の探索・公開予定カレンダー）—— 落とすと構造的に漏れる
3. **新規行の深掘り**（公式まで辿って日付・料金を確定する）
4. **tier B の再確認**
5. **価格比較の深掘り・補助列の穴埋め** ← **最初に捨てるのはここ**

**予算が尽きたら、目標件数に届かないことと、どの工程を打ち切ったかをそのまま
報告する。** 件数を埋めるために未検証の行を足すのは、3スキルが一貫して禁じてきた
失敗そのものである。

### 8.5 再確認できなかった行を、落とさずに残す

予算切れで tier C まで手が回らなかったとき、その行を黙って消すと
「開催中の催しを一覧から落とした事故」になる。次の条件を**すべて**満たす行に限り、
**前回値のまま書き直してよい**。

1. tier が **C**（会期末が1ヶ月以上先・受付の締切が無い・通年開催）である
2. `onsale_*` が空欄である（締切があるものは tier A に上がっているはず）
3. `price_checked` は**前回の日付のまま書く**（今日に更新しない）

3つ目が要点である。`price_checked` は「いつ確認した値か」を利用者に示す列なので、
古い日付のまま出すのが正しい。**今日の日付に書き換えた瞬間、これは
「確認していない値を確認済みに見せる」という、この仕組みが最も嫌う行為になる。**

`status` / `rank` は書き戻さなくてよい。開催状況は表示のたびに開始日・終了日から
計算されるので（設計書 第3.8節）、持ち越した行でも**見た人の「今日」で判定される**。
以前はここで「今日の日付から計算し直す」ことを求めていたが、それは
「収集した日で時間が止まる列」を毎週手で巻き直していただけだった。

前回の全列は `prev_rows.py --uid` で引ける。使った行数は報告に含めること。

> **tier A・B にこの扱いを使ってはいけない。** 変わりやすいと判定された行を
> 確認せずに書き写すことは、`_carry` がスクリプトで拒んでいる行為と同じである。
>
> **この持ち越しが、終了日を過ぎた行をCSVに残す唯一の経路である。** 前回値の
> まま書き直した行が、実はすでに終了日を過ぎていた場合の後始末は、
> `tools/purge_ended.py` に任せる（第5.1節）。

### 8.6 価格比較は「するか」ではなく「どこまでやるか」（events / movies）

第8.1節の実測（126件・収穫7件・値引き0件）が示すのは、比較そのものが無価値だ
ということではなく、**比較に意味がある層が限られている**ということである。
プレイガイドが在庫を持って割引を出すのは、**有料の施設入場券**の層だけで、
そこ以外を同じ密度で当たっても構造的に何も出てこない。

**第0段階（取得0回・判定だけ）** —— 次に当たる行は、比較しない。
`price` に公式の案内を書いて終える。

- 入場無料（寺社の祭事・花火大会・商業施設の催事・マルシェ）
- 飲食・物販が主体で入場自体は無料
- 日別変動価格（変動制パスポート等）—— 横断比較しても意味のある数字が出ない
- チケット制のホール公演 —— 定価固定（ライブ収集で価格比較を行わないのと同じ理由）

**第1段階** —— 公式ページで正規料金を確認し、`price_official` に書く。
**多くの行はここで終わってよい。**

**第2段階（対象層のみ・2サイトまで）** —— テーマパーク・水族館・動物園・
大型企画展など、プレイガイドが通年で券を扱う層に限って、asoview! と
Klook/KKday のどちらか一方を当たる。**差が出なければ、そこで打ち切る**
（`price_best` = `price_official`、`best_source` = `公式サイト`）。

**第3段階（第2段階で差またはクーポンが出たときだけ）** —— 残りのA群を当たる。
安い経路が実在する行にだけ、深掘りの予算を集中させる。

**クーポンページはセッションに1回だけ開く。** asoview!・Klook・KKday等の
クーポン／セール一覧を**各1回**開き、今回の収集対象と突き合わせる。
イベントごとに開き直すと、同じページを100回開くことになる。

### 8.7 予算の守り方 —— 数えるのは機械の仕事

**工程ごとに枠が決まっていれば、セッション全体の回数を数える必要はない。**
工程の中で数えて、枠を使い切ったらその工程を終える——これだけで合計は上限に収まる。
枠の数字は各 SKILL.md の「調査予算」表にある。

ただし**数える手段が、以前はモデルの記憶しかなかった。** 枠表は3スキルの中心的な
統制手段でありながら、守っているかどうかを誰も確認できない。実際 2026-08-14 の実行は
検索115回・取得154回を消費したが、報告には1行も出ていない。

そこで `tools/budget.py` が実測を持つ。工程を切り替えるときに1行打ち、
確認したいときに `--report` を打つ。

```bash
python3 tools/budget.py --phase "ステップ2 エリア軸の探索"   # 以後の計上先を切り替える
python3 tools/budget.py --report                             # いまの消費
python3 tools/budget.py --report --verbose                   # 工程別の内訳つき
```

```
[予算] 検索 63/170（残り107・上限200） / 取得 154（うち拒否2） / 待機 12分 / 追記 34行 / 経過 96分/360分（残り264分）
```

数えているのは `PreToolUse` フックである。`WebSearch` のたびに1回、`WebFetch` のたびに
`fetch_gate.py` が1回、`append_rows.py` が追記のたびに件数を足す。
**待つ処理を `fetch_gate.py` の中に置いたのと同じ理屈で、数える処理をフックの中に置けば、
モデルが数えなくても数えられている。**

報告には**工程別の消費と、打ち切った工程**を含める。`--report --verbose` の出力を
そのまま貼ればよい（記憶で書かない）。

#### 数えていなかったもの、伝えていなかったもの

**取得（`WebFetch`）は数えていなかった。** 枠表は `WebSearch` だけを見ていたが、
実測では取得のほうが多い。しかも `fetch_gate.py` が `Crawl-delay` を消化するので、
**時間の律速は取得側にある**——名簿234施設を一周するだけで、下限3秒×234＝12分が
待ち時間として消える。`Crawl-delay: 120` を宣言しているサイトが混ざれば、
そこだけで数分が飛ぶ。取得の回数と累積待ち時間も同じ器で数える。

**1回の実行に6時間の枠があることも、伝えていなかった。**（`ROUTINE_TIMEOUT_SEC`。
`claude-routine.sh` が export し、`budget.py` が残り時間として出す。）
モデルに届いていたのは「予算が尽きたら打ち切ってよい」「コンテキストが逼迫したら撤退」
だけで、まだ余っていることを知る手段が無かった。実際、2026-08-14 の回は**18分**で
終わっており、正常に完走した 08-12 の回は**5時間27分**を使っている。
**残りを知らせないまま撤退を促せば、早く撤退する。**

### 8.8 検索を使わない調査経路を先に使う

原則1（検索は「URLを知らないとき」にだけ使う）の延長として、**そもそも検索も
`WebFetch` も使わずに済む経路**がある。予算という制約に対して「節約する」以外の
答えを出せるのはここだけなので、先に当たる。

| 経路                                     | 消費    | 何が取れるか                                   |
| ---------------------------------------- | ------- | ---------------------------------------------- |
| `roster.py <名簿> --list --urls`         | 0       | 調査先のURL。**知っているURLを検索し直さない** |
| `prev_rows.py <ds> --uid / --venue`      | 0       | 前回の `official_url` `url`                    |
| `fetch_page.py <URL> --sitemap --since`  | 取得1回 | その施設の**新着ページだけ**                   |
| `fetch_page.py <URL> --ics` / `--events` | 取得1回 | 日付・会場・**中止状態**が構造化された形で     |
| `fetch_page.py <URL> --text`             | 取得1回 | 一覧の構造が崩れない本文（6.5.9）              |
| `fetch_page.py <URL> --links`            | 取得1回 | 詳細ページの絶対URL一覧（6.5.9）               |
| `fill_apple_music.py`                    | 0       | ラインナップの Apple Music リンク              |

**1回の取得から複数の行が取れる経路を優先する。** 施設のカレンダーページ1枚から
その施設の全催しが取れるなら、催しごとに検索するより桁で安い。第8.2節の原則2
（1回の取得で取れるものを全部取る）を、取得手段の選び方にまで広げたものである。

## 9. まとめ：毎回の流れ

```
0. 各 SKILL.md の「調査予算」表を確認する（工程ごとの検索の枠）
1. python3 tools/append_rows.py <ds> --init          （前回分は自動で .prev へ／予算の計測も起点に戻る）
2. python3 tools/prev_rows.py <ds> --worklist        前回分の棚卸し
   └ 先頭に「先週、確認できないまま消えた行」が出る（第5.0節。今週の最優先）
3. python3 tools/roster.py <名簿> --list --urls      今回調べる先（URL付き＝検索不要）
4. 会場ごとに調査 ―― 既存行の再確認と新規の発見を同時に行う
     ├ python3 tools/budget.py --phase "<工程名>"    工程の切り替わりで打つ
     ├ 検索を使わない経路を先に当たる（第8.8節。fetch_page.py の --text / --links / --sitemap / --ics）
     ├ 必須列が揃った行はそこで打ち切る（充足条件・第8.3節）
     ├ 5〜10件ごとに append_rows.py で追記（変更のない列は _carry）
     │   └ 収穫の記録（roster --hit）と [進捗] 行は、このとき自動で出る
     └ 名簿に無い会場を見つけたら roster.py --add
4.5 python3 tools/append_lineup.py                   フェスの日割り（livesのみ）
     ├ 公式ページを fetch_page.py --text で取って機械的に抜く。検索を使わない
     └ python3 tools/fill_apple_music.py             続けて Apple Music リンクを埋める
5. python3 tools/purge_ended.py <ds>                 終了日を過ぎた行を機械的に取り除く（第5.1節）
6. python3 tools/prev_rows.py <ds> --dispose         残った消えた行の説明（5で片付いた分を除く）
7. python3 tools/roster.py <名簿> --gc               名簿の整理
8. python3 tools/diff_data.py <ds>                   差分の確定（説明漏れ・収穫0件があると落ちる）
9. python3 tools/validate_data.py                    ERROR 0 を確認
10. python3 tools/report_stats.py <ds>               充足率と分布（前回比）
11. 報告（8と10の出力をそのまま使う。budget.py --report --verbose も添える）
```

**手順1（`--init`）は手順2（`--worklist`）より必ず先に行う。** `--init` は退避してから
初期化するので、前回データそのものが失われることはない（以前は失われた）。
ただし**先週の `notfound`/`expired` を翌週の最優先として引き継ぐ仕組み（第5.0節）は、
`--init` の中で1世代ぶんローテートされる**——順序を逆にすると、`--worklist` が見るのは
「前々回」のぶんのままになり、直近の未確認行が1週遅れて表示される。

**手順5〜10は「終了工程」である。** 調査（手順4）は予算の都合で打ち切ってよいが、
終了工程は打ち切れない。詳しくは次章。

## 10. 完走 —— セッションを終わらせる手順

### 10.1 調査は打ち切ってよい。終了工程は打ち切れない

第8章の予算は「どこで**調査**をやめるか」を決めるためのものであって、
「どこで**セッション**を終えてよいか」を決めるものではない。この2つは違う。

```
調査（探索・深掘り）   … 予算・コンテキスト・情報源の都合で打ち切ってよい
終了工程（手順5〜10）  … どんな理由があっても飛ばしてはいけない
```

**終了工程はローカルのコマンドだけで完結し、Web検索を1回も使わない。**
だから「検索の予算が尽きたので終了工程を実行できない」ということは起こらない。
むしろ予算切れで終わる週ほど終了工程が要る——打ち切った分だけ、前回行の
持ち越しと `notfound` の記録が必要になるからである。

### 10.2 中断が具体的に何を壊すか

`append_rows.py --init` は `data/*.csv` をヘッダーだけにする。そこから終了工程を
通すまでの間、CSVは未完成の状態にある。ここでセッションを終えると2つが同時に起きる。

1. **その週の成果が保存されない。** `.claude/scripts/claude-routine.sh` は
   `diff_data.py` と `validate_data.py` が通った回だけをコミットし、通らなかった回は
   生成物を `.claude/logs/failed/` に退避したうえで `data/` を実行前の状態に戻す
2. **翌週の差分検知が壊れる。** 切り詰められたCSVが残ると、翌週の `--init` が
   それを「前回分」として `.prev` に退避し、第1章の「静かな欠落を許さない」仕組みが
   土台から効かなくなる

2 を防ぐためにスクリプトが巻き戻す、というのが上の設計である。裏を返せば、
**中断した週は「何も無かった週」になる。部分的な成果は残らない。**

ただし、そこまで行く前に一度止まる。`Stop` フック（`.claude/hooks/verify-data.sh`）が
ターンを終える前に `purge_ended.py`・`validate_data.py`・`diff_data.py` を回し、
落ちていれば理由を返して作業を続けさせる（`purge_ended.py` は判断を要しない
機械的な後始末なので、ここでは検証にかけず先に直接適用する）。**捨てられる前に
直す機会がある**ということであって、終了工程を省いてよいということではない——
連続ブロックは8回で打ち切られるので、そこで直しきれなければ結局その週は失われる
（`docs/DESIGN.md` 第9.1.5節）。

### 10.3 撤退の手順

打ち切りとは、作業の中断ではなく**終了工程へ進むこと**である。

```
1. 調査済みで未追記の行を append_rows.py で書き切る
2. purge_ended.py <ds>  終了日を過ぎた行を先に機械的に片付ける（第5.1節。3の対象を減らせる）
3. diff_data.py <ds> --allow-unexplained  まだ処理していない前回行を出す
4. 残った行を、検索を使わずに片付ける
     ├ まだ載せるべき行 → prev_rows.py <ds> --uid で前回値を引き、
     │                     第8.5節の条件（onsale_* は空欄）で書き戻す
     └ 判断できない行   → --dispose に notfound を記録する
5. --dispose / --gc / diff_data.py / validate_data.py を通す
6. 報告に「打ち切った工程と理由」「持ち越した行数」「notfound の件数」を書く
```

### 10.4 進捗は、ツールが1行ずつ出す

自動実行のログに残る進捗は、**途中で止まったときに「どこまで進んだか」を人間が
判別できる唯一の手がかり**である。

以前はこれをモデルに書かせていた。**3回の実行を通じて1行も出なかった。**
記録をモデルの意志に任せると残らない、というのは名簿のヒット記録（第7章）でも
同じことが起きている。そこで `append_rows.py` が追記のたびに標準エラーへ出す。

```
[進捗] 追記8件（累計34件）/ 検索 63/170（残り107） / 取得 154（うち拒否2） / 待機 12分 / 経過 96分/360分（残り264分）
```

**書き込みが起きた事実から機械的に導けるなら、機械が書く。** 工程名を添えたいときは、
工程の切り替わりで `budget.py --phase "<工程名>"` を打っておけばよい。

## 11. 並行して調べる —— サブエージェントの使い方

**並行調査そのものは禁じない。** 7都県を分割して同時に調べるのは予算配分として
正しく、このタスクの調査能力を伸ばせる数少ない手段でもある。

壊れたのは**起動の形**のほうである。2026-08-14 の events 収集は、4地域の調査を
**背景の**サブエージェントに委ねた。親セッションは結果を待たずに自分のターンを
終えようとし、`Stop` フックに止められて `data/.prev/` から復元し、
「検証が通る状態に戻しました」で終了した。その約1秒後、ログにこう出ている。

```
Background tasks still running after 600s; terminating.
```

**4体ぶんの調査結果は、誰にも受け取られないまま破棄された。** 検索115回・取得154回・
$3.65 を消費して、新規0件・変更0件である。

### 11.1 守ること

| 規則                                                                     | 理由                                                                                            |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| **背景で起動しない**（`run_in_background: false` を明示する）            | 前景なら結果が返るまで親のターンが進まないので、待ち忘れが原理的に起きない                      |
| **親は、全ての結果を `append_rows.py` で書き終えるまでターンを終えない** | 追記していない調査結果は、最初から無かったのと同じ（第10.2節）                                  |
| **サブエージェントは調査のみ。`data/` に書かない**                       | 同じCSVへの同時追記は id の採番と持ち越しの前提を壊す                                           |
| **結果は JSONL で返す**（`append_rows.py` にそのまま渡せる形）           | 親の仕事を「集約して書く」だけにできる                                                          |
| **worktree 隔離を使わない**                                              | サブエージェントは書き込まないので隔離する対象が無い。隔離すると名簿の更新まで破棄される        |
| **1回の呼び出しに、調査軸1つの全体を背負わせない**                       | 呼び出しが長時間に及ぶほど、外部要因による打ち切りが1回分の調査結果を丸ごと失わせる（第11.3節） |
| **1つの波の結果を全部書き切ってから、次の波を投げる**                    | 波をまたいで投げ続けると、打ち切られたときにどこまで書けたか分からなくなる（第11.3節）          |

**「波」とは、同時に起動して同時に受け取る1組のサブエージェントのことである。**
親は波を1つ投げ、**その波の全員が返るのを待ち**、結果を `append_rows.py` で
書き切ってから、次の波を投げる。

```
波1（3体）→ 全員の結果を受け取る → append_rows.py で書く → 波2（3体）→ …
```

以前この節は「1体ずつ呼び、1体ぶんを書いてから次を呼ぶ」と書いていた。
損失を最小にする書き方ではあるが、**同じ節の第11.2節が「7都県を分割して同時に
調べるのは正しい」と書いており、文書内で矛盾していた**。実行時は厳しいほうの
規定が勝つので、並列調査は事実上使えないままだった。

波にすると、失うのは最大でも1波ぶんに閉じる。**この repo が禁じているのは
「誰も受け取らない調査」であって、同時に走ること自体ではない**——
波の全員を待ってから書く限り、受け取られない結果は生じない。

背景起動は `.claude/hooks/agent-guard.sh`（`PreToolUse(Agent)`）が拒否する。
`run_in_background` が未指定のときも拒否する——**Agent ツールの既定は背景起動**なので、
「true のときだけ拒否」では素通りするためである。対話セッションでは発火しない。

### 11.2 分け方

**取得先が重ならない軸で分ける。** 同じホストへ複数のサブエージェントが同時に
当たると、`fetch_gate.py` の間隔制御がホスト単位である以上、互いに待ち合うだけになる。

- ✅ 都県で分ける（施設の所在が重ならない）
- ✅ 名簿の種別で分ける（`museum` / `themepark` / `hall`）
- ❌ 「価格を調べる係」と「日程を調べる係」に分ける（同じページを2回開くことになる）

#### 1波に何体まで —— 上限は数えなくてよい

**この上限は環境変数で与えてあるので、自分で数える必要はない**（検索回数と同じ扱い。
第8.7節）。`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` が実行日のスキルに応じた値で
`.claude/scripts/claude-routine.sh` から渡され、超えた起動は
`Concurrent subagent limit reached` で失敗する。散文でのお願いではなく、
仕組みで担保している。

| スキル       | 名簿                | ユニークホスト数 | 1波の上限 |
| ------------ | ------------------- | ---------------: | --------: |
| events（金） | `spots.csv` 230件   |          **217** |     **3** |
| lives（水）  | `venues.csv` 152件  |          **133** |     **3** |
| movies（木） | `theaters.csv` 85件 |           **25** |     **2** |

**movies だけ低いのは、件数が少ないからではなくホストが少ないからである。**
シネコンは1チェーンの全店舗が同じホストに載っており（85館で25ホスト）、さらに
ステップ1の新作カレンダーは集約サイト数件に取得が集中する。ここで体数を増やしても、
`fetch_gate.py` の待ち行列が伸びるだけで、トークンは体数ぶん増える。

既定値は 20 だが、この収集タスクには過剰である。**並列化で縮むのは待ち時間だけで、
トークンは体数にほぼ比例して増える**（Anthropic のドキュメントも
"Running several sessions or subagents at once multiplies token usage" と明記している）。
20体は、1波が失われたときの損失も 20体ぶんになる。

スキルごとに値を変えられる場所は `claude-routine.sh` しかない——
`.claude/settings.json` の `env` はセッション全体にしか効かず、スキル単位で
差し替える仕組みが存在しないためである。シェルの環境変数は `settings.json` より
優先されるので、当日の値はスクリプトが決める。

**孫エージェントは禁止してある**（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`、
`.claude/settings.json`）。親が待ち切れる保証があるのは、親が直接起動した子までである。
子がさらに孫を産むと、親から見えない場所で「誰にも受け取られない調査」が復活する。

### 11.3 前景でも、1回の範囲が大きすぎると同じことが起きる

2026-08-20 の movies 収集は、背景起動はしていなかった（3体とも
`run_in_background: false` を明示していた）。それでも前回123件のほぼ全件が
「説明のない消滅」として `diff_data.py` に検出され、`Stop` フックが差し戻した。

原因は範囲の切り方である。「名画座・単館ロースター調査」「新作ロードショー網羅調査」
「特別上映・野外・映画祭調査」という3軸それぞれの全体（85館・対象期間6ヶ月分）を
1回のサブエージェント呼び出しに丸ごと背負わせ、親は3体分の結果を JSONL で受け取って
から `append_rows.py` でまとめて書く設計にしていた。開始から約12分後、アカウントの
利用上限（`You've hit your session limit`）で3体とも打ち切られ
（`Agent terminated early due to an API error`）、親セッションも同時に終了した。
この時点で `append_rows.py` への追記は `--init` の1回のみで、前回分は1件も
書き戻されていなかった——3体とも「軸を調べ終えてから返す」設計だったため、
親が途中経過を受け取る機会が最後まで来なかったことが理由である。

本番データは `Stop` フックが HEAD へ差し戻したため実害はない。ただし、その週の
収集は丸ごと失われた（第10.2節の「中断した週は『何も無かった週』になる」が
そのまま起きている）。

**背景起動の禁止だけでは、この壊れ方は防げない。** 前景であっても、1回の呼び出しが
長時間に及ぶ設計なら、外部要因（アカウントの利用上限・API障害・ネットワーク断）に
よる打ち切りは呼び出しの途中でいつでも起こり得て、そのとき戻せる結果が何も無い。
守るのは呼び出しの粒度でもある——1回のサブエージェント呼び出しが背負う範囲を、
名簿の一部・対象期間の一部などに区切り、親は**1つの波を受け取るごとに**
`append_rows.py` で書き切ってから、次の波を投げる。

**この事故が示しているのは「体数が多すぎた」ことではない。** 3体は上限
（movies は2体）に照らしても多くないが、**1体が6ヶ月分・85館を丸ごと背負い、
返るまで親に何も渡さなかった**ことが原因である。体数の上限と、1体が背負う範囲は
別の縛りであり、**両方を守って初めて損失が波1つぶんに収まる。**

## 12. 収穫を測る —— 空回りを成功と区別する

### 12.1 「壊れていないか」と「何か産んだか」は別の検査

`validate_data.py` と `diff_data.py` は、長らく前者しか見ていなかった。
2026-08-14 の回は、前回のCSVをそのまま復元して終わったので**壊れてはおらず**、
検証を素通りして「週次データ更新」としてコミット・pushされた。

そこで `diff_data.py` は、**`--init` を今日実行したデータセット**——つまり今回の
収集対象——について、新規・変更・消滅が**すべて0件**なら終了コード1を返す。
100件規模のCSVで1週間分の変化が3種類とも0になるのは、`purge_ended.py` が
終了日を過ぎた行を消すことすら起きなかったということで、収集が実質的に走らなかった形である。

調査の途中で確認したいときは `--allow-noop` を付ける。**最終判定で付けてはいけない。**

> 1日1スキルしか回さないので、残り2つのデータセットが無変化なのは正常である。
> そこまで異常扱いにすると、毎回必ず落ちるだけの検査になる。

### 12.2 件数は中身の薄さを隠す

各スキルは報告に「件数・都県別内訳・カテゴリ別内訳」を求めていた。だが件数だけを
見ていると、次の状態が「100件そろっている健全な週」に見える（2026-08 の実測）。

|                      | 充足率     | そのスキル自身の記述                                                     |
| -------------------- | ---------- | ------------------------------------------------------------------------ |
| events `price_best`  | 6/113 (5%) | 「このタスクの最も重要な仕事」                                           |
| events `coupon_note` | 2/113 (1%) | 同上                                                                     |
| lives `onsale_end`   | 2/90 (2%)  | 「この列の精度がこのタスクの価値を決める」                               |
| movies の拡張列      | 0/130 (0%) | `price_*` `onsale_*` `kana` `series_id` `announced_date` `is_additional` |

`tools/report_stats.py` は、各スキルが自分で中核だと言っている列の充足率を、
前回のCSVと並べて出す。

```bash
python3 tools/report_stats.py events
```

```
中核列の充足率（前回比）
  price_best            6/113    5%  → 前回  5%  （最安経路の総額）
  coupon_note           2/113    1%  → 前回  1%  （配布中クーポン）
```

**「調査能力が落ちている気がする」を「先週5%から今週3%に落ちた」に変えるための道具**である。
報告にそのまま貼る。数字が下がった週は、`docs/skill-feedback.md` に書くべきことが
実在するという合図でもある。

「7都県すべてから5件以上」「東京は半分以下」といった品質チェックの項目も、
ここで機械が数える。**数えられるものは数える。**
