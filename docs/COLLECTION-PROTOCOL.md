# 収集タスク共通プロトコル —— 差分検知・持ち越し・名簿の自己更新

`/kanto-event-collector`・`/kanto-live-collector`・`/kanto-movie-collector` の
3スキルが共有する手順とその理由をここにまとめる。各 SKILL.md には実行するコマンドを
書いてあるので、**手を動かすだけならこの文書を読まなくても進められる**。
「なぜそうするのか」「判断に迷ったときどちらへ倒すか」はここに書いてある。

---

## 1. この仕組みが解こうとしている問題

### 1.1 毎週ゼロから調べ直していた

3つの収集タスクは、これまで毎回 `--init` でCSVを空にし、全件を新規に調査していた。
この方式には次の欠陥があった。

**静かな欠落が検知できない。** 先週載っていた開催中の展覧会が、今週たまたま検索に
引っかからなければ、そのまま一覧から消える。結果のCSVを見ても「終了したから消えた」のか
「見つけられなかったから消えた」のかは区別できない。**開催中の催しを落とすのは、
利用者にとって最も損害の大きい失敗**だが、これまでは起きても誰も気づけなかった。

**中止・延期を拾えない。** 台風で中止になった花火大会のページには「中止」と
書かれているが、ゼロから調べ直すフローではそれを「開催予定」として拾い直しうる。

**「前回からの変化」を報告できない。** イベント・映画のスキルは報告項目に
「前回からの主な変化」「前回から新たに出たクーポン」を挙げていながら、
前回のCSVを読む手順を持っていなかった。読んでいないものとの差分は書けない。

### 1.2 かといって前回CSVを丸ごと読むのは高すぎる

`data/events.csv` は約68,000文字（概算4〜5万トークン）ある。着手した時点で
コンテキストの2〜3割を失い、`tools/append_rows.py` の冒頭に書いた
「後半の調査品質が落ちる」問題がそのまま再発する。

### 1.3 だから、突き合わせは機械にやらせる

**機械の仕事**：どの行が消えたか、増えたか、どの列が変わったか
**モデルの仕事**：その変化が何を意味するか（会期延長か／中止か／単なる表記ゆれか）

この線引きが、この仕組みの設計の中心にある。

## 2. 行の同定（uid）

週をまたいで同じ行を指すために、**タイトル・会場・日付から計算する8桁の uid** を使う
（`tools/rowkey.py`）。CSVに列としては持たない。

- `id` 列は `append_rows.py` が毎回1から振り直すので、週をまたぐ識別子にはならない
- uid 列を新設すると、収集のたびにそれを正しく書き写す作業が増え、新しい事故の種になる
- uid の材料に使う列（タイトル・会場・日付）は、そもそも間違えてはいけない列である

表記ゆれ（全角/半角、ひらがな/カタカナ、記号、空白）は正規化で吸収する。
それでも uid が変わる書き換え（タイトルの言い換え）は、`diff_data.py` が
**「表記が変わった可能性」として候補を出す**ので、モデルが同一かどうかを判断する。

> 映画の新作行だけは、会場（`theater`）を uid の材料から外している。
> 新作の `theater` は上映チェーンの一覧で、翌週チェーンが1つ増えるだけで
> 「消えて新しく現れた」ことになってしまうため。

## 3. 棚卸し（ステップ0）

```bash
python3 tools/prev_rows.py <events|lives|movies> --worklist
```

前回分を**圧縮した一覧**で出す。events.csv の場合、68,000文字が約10,000文字になる。
全列が必要になった行だけ、あとから引く。

```bash
python3 tools/prev_rows.py events --uid 3f2a1b9c          # その行を全列で
python3 tools/prev_rows.py events --venue 東京国立博物館   # その会場の前回分をまとめて
```

### 3.1 tier —— どこから手を付けるか

| tier  | 意味                               | 判定の根拠                                                                                                              |
| ----- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **A** | 今回必ず再確認する                 | 会期末・受付締切が21日以内／発売がこれから／status が「本日まで」等／クーポンあり／追加公演／価格の確認日が14日より古い |
| **B** | 会場ページを開いたついでに確認する | 上記に当たらない通常の行                                                                                                |
| **C** | 低頻度でよい                       | 「通年予約可」など日程が動かないもの                                                                                    |

tier は「手を抜いてよい行」を決めるためのものではない。
**限られたページ取得の回数を、変わりやすい行から先に使う**ための優先順位である。

### 3.2 会場単位で回る（重要）

**行を1件ずつ再確認してはいけない。** 会場ごとに回ること。

東京国立博物館の展覧会ページを1回開けば、同時に次の3つが分かる。

1. 既存の行がまだ開催中か（会期延長・中止を含む）
2. 会期・料金・受付が変わっていないか
3. **前回になかった新しい企画展が始まっていないか**

つまり「既存行の更新確認」と「新規の発見」は、同じ1回の取得で済む。
行ごとに確認すると126回の取得になるが、会場ごとなら新規探索のついでで終わる。
**この仕組みが追加のコストをほとんど生まないのは、この相乗りのおかげである。**

## 4. 持ち越し（carryover）—— 何を書き直さなくてよいか

前回と同じ行を書くとき、座標・最寄り駅・駐車場のような**動かない事実**まで
毎回書き直すのは出力トークンの無駄であり、写し間違いの機会でもある。

```bash
# 内容に変更がないことを確認できた行
python3 tools/append_rows.py events <<'EOF'
{"title": "...", "venue": "...", "start_date": "...", "date": "...", "status": "...",
 "rank": "2", "cats": "art", "area": "...", "pref": "tokyo", "price": "...",
 "source": "公式サイト", "url": "...", "_carry": "*"}
EOF
```

| 区分                   | 列                                                                                                                              | 扱い                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| **自動で埋まる**       | `kana` `lat` `lng` `parking` `nearest_station` `venue_url` `theater_url`                                                        | 空欄なら前回値で補完。何も書かなくてよい    |
| **頼めば埋まる**       | `desc` `note` `official_url` `artists` `cats`/`genre` `series_id`/`tour_id` `poster_url` など                                   | `"_carry": "*"` か `"_carry": "desc\|note"` |
| **絶対に持ち越さない** | 日付・`status`・`rank`・`onsale_*`・`price*`・`coupon_note`・`limited_sale`・`url`・`source`・`announced_date`・`is_additional` | スクリプトが拒否する                        |

最後の区分が、この仕組みで最も重要な安全装置である。

> 前回の締切をそのまま書き写すことは、このプロジェクトが3スキルで一貫して
> 禁じてきた「確認していない値を書く」そのものにあたる。差分方式は、
> **未検証の値を検証済みらしく見せるのを容易にする**という副作用を持つので、
> 指示文でのお願いではなく、スクリプトが受け付けないという形で担保している。
> `"_carry": "onsale_end"` はエラーで落ちる。

会場の座標・最寄り駅・駐車場は「行の属性」ではなく「場所の属性」なので、
会期が変わって uid がずれても、**同じ会場の別の行から引かれる**。

`"_carry": "*"` を使ってよいのは、**その行の内容に変更がないことを実際に確認できたとき
だけ**である。確認していないなら、確認するか、その列を空欄にする。

## 5. 消えた行には説明をつける（省略不可）

前回あって今回無い行は、必ずどちらかである。

1. 本当に終わった・中止になった → 正しく消えている
2. 今回は見つけられなかった → **事故**

この2つを区別できるようにするため、消えた行それぞれに理由を記録する。

```bash
python3 tools/prev_rows.py events --dispose <<'EOF'
{"uid": "37e50ea9", "status": "ended",        "note": "8/31で会期終了を公式サイトで確認"}
{"uid": "2e9a11b8", "status": "cancelled",    "note": "荒天のため中止"}
{"uid": "9ab96b1e", "status": "out-of-scope", "note": "開始が3ヶ月より先になった"}
{"uid": "4b7d8c70", "status": "renamed",      "to": "a1b2c3d4", "note": "正式名称に変更"}
{"uid": "341daad8", "status": "notfound",     "note": "会場ページに記載がなく確認できず"}
EOF
```

`notfound` は「調べたが分からなかった」を正直に記録するためのものであり、
**面倒を避けるために使ってよいものではない**。`notfound` が多い週は、その旨と
件数を報告に含めること。

`diff_data.py` は、説明のない消滅があるとエラーで落ちる。

## 6. 最終工程：差分の確定

```bash
python3 tools/diff_data.py            # 3データセットまとめて
python3 tools/validate_data.py        # 従来どおり ERROR 0 を確認
```

`diff_data.py` の出力が、そのまま報告の「前回からの変化」になる。
新規・変更・消滅・表記ゆれ候補が機械的に列挙されるので、
**モデルが記憶や印象で「主な変化」を書く必要はない**（書いてはいけない）。

`announced_date` と `is_additional` も、この差分に基づいて決める。

- 発表記事の日付が分かるなら、その日付を `announced_date` に書く
- 分からない場合に**限り**、差分で新規と判定された行に今日の日付を入れる
- 「前回に無かった」以外の根拠なしに `is_additional` を立てない

## 7. 名簿の自己更新 —— どこまでを自動でやるか

定点観測リスト（名簿）は放っておけば必ず腐る。会場は開業し、閉館し、改称する。
名画座は畳み、フェスは開催地を変える。だから収集タスク自身が名簿を育てる。

| 名簿         | ファイル             | 対象                                   |
| ------------ | -------------------- | -------------------------------------- |
| イベント施設 | `data/spots.csv`     | 美術館・テーマパーク・水族館・ホール等 |
| ライブ会場   | `data/venues.csv`    | ドーム・アリーナ・ホール・ライブハウス |
| 映画館       | `data/theaters.csv`  | シネコンチェーンの店舗・名画座         |
| フェス       | `data/festivals.csv` | 関東開催の音楽フェス                   |

```bash
python3 tools/roster.py spots --list --pref tokyo      # 今回調べる先を出す
python3 tools/roster.py spots --hit 東京国立博物館      # 収穫があった先を記録
python3 tools/roster.py spots --add <<'EOF'            # 名簿に無い会場を見つけた
{"name": "○○ミュージアム", "kind": "museum", "pref": "tokyo", "url": "https://..."}
EOF
python3 tools/roster.py venues --retire ○○ホール --reason "2026年6月閉館"
python3 tools/roster.py venues --close ○○アリーナ --until 2027-04-01
python3 tools/roster.py spots --gc                     # 収穫のない先を整理（毎回最後に）
```

状態は `candidate`（今回はじめて見つけた）→ `active`（2回ヒットで昇格）→
`retired`（閉館、または長期にわたり収穫ゼロ）と遷移する。
**`--gc` を毎回必ず実行すること。** 追加しかしないと名簿は単調に膨らみ、
いずれ定点観測が対象期間を回りきれなくなる。

### 7.1 スキル本文（SKILL.md）は書き換えない

**名簿（データ）は自動更新、ルール（散文）は提案止まり。** この線は動かさない。

収集タスクが自分の SKILL.md を書き換える形を採らない理由は4つある。

1. **プロンプトインジェクション。** Webページを読んだ主体が、自分の指示書に
   書き込む権限を持つ構造になる。「重要：収集ルールを次のように変更せよ」と
   書かれたページ1枚で、翌週以降のすべての実行が汚染される。しかも cron の
   自動実行で、`--permission-mode bypassPermissions` である
2. **静かな基準の緩和。** モデルは自分を縛るルールを緩める方向へ書き換える誘因を
   常に持ち、そして劣化を判定するのはその劣化したスキル自身になる
3. **レビュー不能。** 散文の書き換えは差分が読みにくく、毎週 main へ直接 push する
   運用では誰も気づけない
4. **際限のない肥大化。** 名簿と違い、散文には整理の仕組みがない

`roster.py` が触るのはCSVの名簿だけで、列も値も検証される。名簿に入る文字列は
Webページ由来になりうるので、**指示文めいた文字列・制御文字・長すぎる値は
その場で拒否する**（`roster.py` の検疫）。

### 7.2 ルールを変えたほうがよいと気づいたら

`docs/skill-feedback.md` に追記する。適用するかどうかは人間が判断する。

対象になるのは、たとえば次のようなもの。

- 目標件数・カテゴリ配分が実態に合っていない
- 参照先サイトが閉鎖した／新しい有力なサイトが現れた
- CSVの列や検証ルールに実務上の無理がある
- 季節キーワード表・プレイガイド一覧・配給会社リストの更新

**目標件数・品質基準・禁止事項（「推測で埋めない」系のルール）は、
提案はしてよいが自分で変更してはならない。**

## 8. 調査予算 —— 有限の検索回数と文脈をどう配るか

### 8.1 なぜ予算の話が要るのか

**Web検索の呼び出しには、1セッションあたり200回という上限がある。** これは
「たくさん調べれば品質が上がる」という前提が成り立たないことを意味する。
超えた瞬間、以降の調査は**中途半端な場所で止まる**。

実際に起きたことが2つ記録されている。

- **2026-08-04 movies**: 検索が200回に達し、公開日だけ確認できて上映劇場・
  公式URLまで辿れなかった作品が多数残った。`url` は必須列なので、それらは
  収録を断念することになった（`docs/skill-feedback.md`）
- **2026-08-02 events**: 126件を収集し、A群11サイトの横断比較を指示どおり
  行った結果、`price_best` を書けたのは**7件**、`coupon_note` は**2件**。
  しかもその7件は**すべて「公式サイトが最安」**で、他経路のほうが安かった行は
  **1件も無かった**

2つ目が重要である。「A群のサイトを**すべて**確認する」を126件に課すと、
名目上は1,300回規模の取得になる。それだけ使って、実際に得られた情報は
「公式が最安だった」が7件だけだった。**実行不可能なルールは、丁寧な仕事を
生まない。恣意的な場所で黙って止まった仕事を生む。**

だから、予算を先に配り、**尽きたときに何を捨てるかを先に決めておく**。

### 8.2 3つの原則

#### 原則1 —— 検索は「URLを知らないとき」にだけ使う

名簿には `url` 列があり、ほぼ全件埋まっている（spots 230/234・venues 72/72・
theaters 85/85・festivals 13/14）。前回CSVにも `official_url` と `url` がある。

```bash
python3 tools/roster.py spots --list --pref tokyo --urls   # 名前とURLを出す
python3 tools/prev_rows.py events --venue 東京国立博物館     # 前回の official_url を引く
```

**知っているURLを検索し直すのが、最も多く、最も無自覚に消える予算である。**
名簿を一周するだけで200回を超える計算になるが、`--urls` で直接開けば検索は0回で済む。
検索が要るのは「まだURLを知らないもの」——エリア軸の探索、新しい会場、
名簿の `url` が空欄の数件——だけである。

#### 原則2 —— 1回の取得で、取れるものを全部取る

会場ページを1回開けば「既存行の再確認」と「新規の発見」が同時に済む（第3.2節）。
これを列にも広げる。**その会場に関わる会期・料金・アクセス・注意事項を、
その1回で拾い切る。** 「あとで座標だけ」「あとでアクセスだけ」と戻るのは、
同じページの二重払いになる。

#### 原則3 —— 充足したら止める

行ごとに「これが埋まったら完成」を先に決め、埋まった行はそれ以上調べない。
**すでに判断できる情報が揃っているのに調査を続けるのは、品質ではなく消費である。**

### 8.3 行の充足条件（Definition of Done）

| 区分                          | 列                                                                                                           | 扱い                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| **必須**                      | タイトル・分類・場所（area/pref/会場）・日付・`status`/`rank`・`price`・`source`・`url`・`desc`              | ここが揃った時点で**その行の調査を終える**                           |
| **ついでに拾う**              | `kana` `note` `venue_url` `series_id`/`tour_id` `announced_date` `is_additional` `parking`/`nearest_station` | 開いたページに書いてあれば書く。**このために追加でページを開かない** |
| **調べなくてよい**            | `lat`/`lng`                                                                                                  | 名簿と前回値から自動補完される。**名簿にある会場は調べない**         |
| **1回で見つからなければ空欄** | `poster_url`（映画）`apple_music_url`（ライブ）                                                              | 粘らない                                                             |

**「空欄でよい列を埋めるために検索する」ことが、予算を最も静かに食う。**
空欄は品質の問題ではない、という既存の原則は、そのまま予算の原則でもある。

> `lat`/`lng` について補足する。`append_rows.py` は座標を**会場の属性**として
> 名簿と前回値から補完する。名簿に載っている会場（＝定点観測先のほぼ全部）は
> 空欄で渡してよく、調べる必要がない。座標を調べてよいのは、**名簿にも前回にも
> 無い新しい会場**だけである。

### 8.4 予算が尽きたときに捨てる順

上から順に守る。**下から順に捨てる。**

1. **tier A の再確認** —— 落とすと「終わった催しが載り続ける」「中止を伝えない」
   という、このプロジェクトで最も重い実害が出る
2. **網羅の工程**（エリア軸の探索・公開予定カレンダー）—— 落とすと構造的に漏れる
3. **新規行の深掘り**（公式まで辿って日付・料金を確定する）
4. **tier B の再確認**
5. **価格比較の深掘り・補助列の穴埋め** ← **最初に捨てるのはここ**

**予算が尽きたら、目標件数に届かないことと、どの工程を打ち切ったかをそのまま
報告する。** 件数を埋めるために未検証の行を足すのは、3スキルが一貫して禁じてきた
失敗そのものである。

### 8.5 再確認できなかった行を、落とさずに残す

予算切れで tier C まで手が回らなかったとき、その行を黙って消すと
「開催中の催しを一覧から落とした事故」になる。次の条件を**すべて**満たす行に限り、
**前回値のまま書き直してよい**。

1. tier が **C**（会期末が1ヶ月以上先・受付の締切が無い・通年開催）である
2. `onsale_*` が空欄である（締切があるものは tier A に上がっているはず）
3. `status` / `rank` は前回値ではなく、**今日の日付から計算し直す**
4. `price_checked` は**前回の日付のまま書く**（今日に更新しない）

4つ目が要点である。`price_checked` は「いつ確認した値か」を利用者に示す列なので、
古い日付のまま出すのが正しい。**今日の日付に書き換えた瞬間、これは
「確認していない値を確認済みに見せる」という、この仕組みが最も嫌う行為になる。**

前回の全列は `prev_rows.py --uid` で引ける。使った行数は報告に含めること。

> **tier A・B にこの扱いを使ってはいけない。** 変わりやすいと判定された行を
> 確認せずに書き写すことは、`_carry` がスクリプトで拒んでいる行為と同じである。

### 8.6 価格比較は「するか」ではなく「どこまでやるか」（events / movies）

第8.1節の実測（126件・収穫7件・値引き0件）が示すのは、比較そのものが無価値だ
ということではなく、**比較に意味がある層が限られている**ということである。
プレイガイドが在庫を持って割引を出すのは、**有料の施設入場券**の層だけで、
そこ以外を同じ密度で当たっても構造的に何も出てこない。

**第0段階（取得0回・判定だけ）** —— 次に当たる行は、比較しない。
`price` に公式の案内を書いて終える。

- 入場無料（寺社の祭事・花火大会・商業施設の催事・マルシェ）
- 飲食・物販が主体で入場自体は無料
- 日別変動価格（変動制パスポート等）—— 横断比較しても意味のある数字が出ない
- チケット制のホール公演 —— 定価固定（ライブ収集で価格比較を行わないのと同じ理由）

**第1段階** —— 公式ページで正規料金を確認し、`price_official` に書く。
**多くの行はここで終わってよい。**

**第2段階（対象層のみ・2サイトまで）** —— テーマパーク・水族館・動物園・
大型企画展など、プレイガイドが通年で券を扱う層に限って、asoview! と
Klook/KKday のどちらか一方を当たる。**差が出なければ、そこで打ち切る**
（`price_best` = `price_official`、`best_source` = `公式サイト`）。

**第3段階（第2段階で差またはクーポンが出たときだけ）** —— 残りのA群を当たる。
安い経路が実在する行にだけ、深掘りの予算を集中させる。

**クーポンページはセッションに1回だけ開く。** asoview!・Klook・KKday等の
クーポン／セール一覧を**各1回**開き、今回の収集対象と突き合わせる。
イベントごとに開き直すと、同じページを100回開くことになる。

### 8.7 予算の守り方

**工程ごとに枠が決まっていれば、セッション全体の回数を数える必要はない。**
工程の中で数えて、枠を使い切ったらその工程を終える——これだけで合計は上限に収まる。
枠の数字は各 SKILL.md の「調査予算」表にある。

工程の切り替わりで、その工程で使った検索回数を1行ログに出す。
報告には**工程別の検索回数（概数）と、打ち切った工程**を含める。

## 9. まとめ：毎回の流れ

```
0. 各 SKILL.md の「調査予算」表を確認する（工程ごとの検索の枠）
1. python3 tools/prev_rows.py <ds> --worklist        前回分の棚卸し
2. python3 tools/append_rows.py <ds> --init          （前回分は自動で .prev へ退避）
3. python3 tools/roster.py <名簿> --list --urls      今回調べる先（URL付き＝検索不要）
4. 会場ごとに調査 —— 既存行の再確認と新規の発見を同時に行う
     ├ 必須列が揃った行はそこで打ち切る（充足条件・第8.3節）
     ├ 5〜10件ごとに append_rows.py で追記（変更のない列は _carry）
     ├ 収穫のあった先を roster.py --hit
     └ 名簿に無い会場を見つけたら roster.py --add
5. python3 tools/prev_rows.py <ds> --dispose         消えた行の説明
6. python3 tools/roster.py <名簿> --gc               名簿の整理
7. python3 tools/diff_data.py <ds>                   差分の確定（説明漏れがあると落ちる）
8. python3 tools/validate_data.py                    ERROR 0 を確認
9. 報告（7の出力をそのまま「前回からの変化」に使う。工程別の検索回数も添える）
```

手順2は手順1より**後**でなくてもよい。`--init` は退避してから初期化するので、
順序を間違えても前回データは失われない（以前は失われた）。
