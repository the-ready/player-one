# 週次ルーチンの事故記録

無人実行で実際に起きた壊れ方と、それをどう塞いだかの記録である。

**ここは実行時には読ませない。** 規則そのものは
[`.claude/routines/invariants.md`](../.claude/routines/invariants.md)（システムプロンプトに載る）と
[`.claude/skills/weekly-routine/SKILL.md`](../.claude/skills/weekly-routine/SKILL.md)（手順）にあり、
この文書はその**根拠**を保つためだけに存在する。規則を緩めたくなったとき、
何を失って得た規則なのかをここで確認する。

規則を散文で伝えるのではなくフックに置く、という方針の理由は `DESIGN.md` 第9.1.5節にある。
以下のうち、散文の指示だけで防げていたものは**一件も無い**。

## 2026-08-14 events —— 背景起動したサブエージェントが、誰にも受け取られずに消えた

4地域の調査を背景のサブエージェントに委ね、親が結果を待たずに自分のターンを終えようとした。
`Stop` フック（`--init` 直後の未完成CSVを検知）に止められて `data/.prev/` から復元し、
「検証が通る状態に戻しました」で終了。その約1秒後にログへ

    Background tasks still running after 600s; terminating.

が出ている。**4体ぶんの調査結果は、誰にも受け取られないまま破棄された。**
検索115回・取得154回・$3.65 を消費して、新規0件・変更0件。

**原因は「親が待てなかったこと」に尽きる。** 背景起動は親に待つ義務を課さない——待つかどうかが
モデルの判断に委ねられ、判断を誤っても誰も気づけない。

**塞ぎ方**: `.claude/hooks/agent-guard.sh` が `run_in_background: false` の明示されていない `Agent` 起動を拒否する。
既定が背景起動なので「true のときだけ拒否」では素通りする。**既定値に依存しない書き方を求めている。**

## 2026-08-20 movies —— 前景起動でも、1回に全体を背負わせれば同じように全損する

3軸それぞれの全体（85館・6ヶ月分）を1回の呼び出しに丸ごと背負わせ、3体分の結果をまとめて受け取ってから
`append_rows.py` で書く設計にしていた。開始12分後にアカウントの利用上限（`session limit`）で3体とも打ち切られ、
`--init` 以降 `append_rows.py` への追記が一度もないまま終わった。前回123件のほぼ全件が「説明のない消滅」として
検出され、`Stop` フックが差し戻している（本番データへの実害はない）。

**背景起動の禁止だけでは、1回の呼び出しが長時間に及ぶ設計までは守れない。**
区切るのは起動の形だけでなく、1回に背負う範囲でもある（`COLLECTION-PROTOCOL.md` 第11.3節）。

## 2026-08-27 movies —— 調べ終えた90行が、CSVに1行も入らなかった

    02:53  子: temp/rows-... に44件を書く
    02:53  子→親: 「44件書いた」
    02:53  親: 「44件を書き出しました。続けて2体並行で調査します」
    02:54  親: 次の波を起動          ← append_rows.py を挟んでいない
    03:04  子: さらに46件を書く
    03:08  利用上限で強制終了

あとで追記して検証を流し直すと通る——**収集は成功していて、受け取りだけが抜けていた。**
「1つの波を書き切ってから次を投げる」は各SKILL.mdが以前から書いている規則で、**書いてあるだけでは守られなかった。**

この抜け方は、結果の受け渡しをファイルに変えた（親の文脈を経由させない）ことで起きやすくなった側面がある。
子が返答本文に行を載せていた頃は、親が書き写す以外に行を扱う道が無く、**追記が避けて通れない工程だった**。
ファイルに移した瞬間、行は親が一度も触らない場所へ移り、「44件書いた」が完了として読めるようになった。
消したのは無駄な往復だが、同時に「必ず通る道」も消していた。

同じ回で、40M の警告を受け取った**3分16秒後**に殺されている。しかも警告が届いた時点で親は波の帰りを待って
停止中で、動いている子に割り込む手段が無かった。**間に合う位置に置くには、「次の波を投げるかどうか」を
決める前に鳴る必要がある。**

子のターン数の実測は 196 / 110 / 120。1つの文脈でN回呼ぶと入力はNの2乗で増えるので、担当範囲を小さく割るだけで
トークンが減る。また `temp/` に367ファイルが溜まっており、子が `ls temp/` を実行して**その全件を自分の文脈に
取り込んでいる**。

**塞ぎ方**: `tools/wave_gate.py` が波のファイルの uid を数え、CSVに入っていなければ次の `Agent` 起動を拒否する。
線は2段階（25M で新しい波をやめ、40M で撤退）にし、`agent-guard.sh` が25Mを越えた起動を機械的に止める。
`claude-routine.sh` は起動のたびに `temp/` の2日より古いファイルを片付ける。

同じ回で、経過18分／360分・文脈再送は最終値17.3M（25M線の約7割）と**両方の線にまだ届いていないまま**、
4波をこなしたことだけを理由に終了工程へ入っていた。**「予定していた波数をこなした」は畳んでよい理由にならない。**

そのまま注入する。無人実行ではさらにスクリプトが決めた `ROUTINE_SKILL` を渡す。

## 2026-09-02 events —— 抜粋を貼らずに自作の指示へ要約し、料金の列が丸ごと落ちた

親（Haiku）は `tools/skill_brief.py events` を実行している。だが抜粋は100,676バイトあり、
Bash の出力上限を超えて `tool-results/` のファイルに落ちた。親はそれを Read したうえで、
4体ぶんの指示に貼る代わりに**自分で1〜2KBに要約した**。

要約から落ちたのは料金だった。子に渡された列の一覧はこうである。

    title, cats, area, venue, pref, start_date, end_date, price, source, url, official_url, desc

`price_official` `price_checked` `price_best` `coupon_note` は**一語も無い**。
価格への言及は「公式料金を確認できた行は記録する」という努力目標の一文だけだった。
**子は書けと言われていない列を書けない。**

結果は、新規90件のうち `price_official` **0件**・`price_checked` **0件**・`price` 29件（32%）。
取得114回のURLを全数照合すると、**料金・チケット・入館料のページは1枚も無い**（全部トップページか
イベント一覧ページ）。`fetch_page.py` は0回で、子は全部 `WebFetch` を使っている——あれは要約を返すので、
表で書かれた金額は要約に載らなければ二度と手に入らない。

**「駐車場や最寄り駅は拾えている」ように見えたのは錯覚だった。** 子が書いた114行のうち
`parking` `nearest_station` `lat` を書いた行は**0行**である。CSVで埋まっている分は全部
`append_rows.py` の `CARRY_ALWAYS`（会場に紐づく事実の自動補完）が入れたもので、
`price` は `CARRY_NEVER` にあるため機械が埋められない。**調査能力の差ではなく、
機械補完の有無の差**が見えていた。

止まる場所は一つも無かった。`validate_data.py` は `price` の空欄を見ない（見るのは
「価格があるのに `price_checked` が無い」の逆向きだけ）。`report_stats.py --check` は
都県の網羅性しか判定しない。`report_stats.py` の events の CORE には**画面に出る `price` 列が
入っていなかった**ので、66%→58% の低下はどの数字にも出ていない。ERROR 0 で通り、コミットされた。

予算は余っていた。検索17/170・取得111回・経過9分/360分・文脈再送12.3M（25M線の半分）。
**予算不足で価格を捨てたのではなく、予算を使わずに畳んでいる。**
そのうえで最終報告は「打ち切った工程: なし。全工程を計画通り実行」「✅ クーポン定点観測: 7社各1回確認」
と書いた——プレイガイドへの取得は**0回**である。指示の組み立ても報告も、親の側の仕事がまとめて崩れていた。

**塞ぎ方**（4つとも、散文の指示ではなく仕組みに置いた）:

| 何を                                                         | どこに                                                                        |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| 抜粋を貼らせない（`--out` でファイルに書き、パスだけを渡す） | `tools/skill_brief.py`。参照が無い波は `agent-guard.sh` が拒否する            |
| 抜粋を小さくする（表の整列余白を潰して32%減）                | `tools/skill_brief.py`（規則は1文字も減らない。`skill_brief_test.py` が固定） |
| 今週の新規行の `price` に下限を置く                          | `report_stats.py --check-fresh` を `verify-data.sh`（Stop フック）が回す      |
| 親を Sonnet・子を Haiku に分ける                             | `schedule` ブロックの5列目 → `CLAUDE_CODE_SUBAGENT_MODEL`                     |

**下限の門はコミット側に置いていない。** あちらで落とすと `data/` が巻き戻り、
価格が薄いことを理由にその週の収集がまるごと消える——薄い週より悪い結果になる。

## 2026-09-03 movies —— 認証切れの回が、「収集の失敗」に見えた

OAuth のリフレッシュトークンが起動の79分前（01:11）に失効しており、02:30 の起動は
`Failed to authenticate: OAuth session expired and could not be refreshed` で
4秒後に終わった。**ツール呼び出しは0件**で、セッションは1度も動いていない。

問題は、そのあとの工程がふだんどおり走ったことである。打ち切られた回を救うための
安全網（`carry-rest` → `purge_ended`）が data/ を書き換え、`quarantine_and_restore`
がそれを巻き戻すので、ログの結びはこうなった。

    ERROR: 実行または検証に失敗したため、コミットも push も行いません
    検証を通らなかった生成物を .claude/logs/failed/20260903-023015 に退避しました
    data/ docs/ を HEAD の内容に戻しました

**調べもしなかった回が、「検証に落ちた回」として記録される。** 読んだ人は収集側の
不具合を探すことになり、実際に必要な対処（ログインし直す）にはたどり着けない。
原因が違えば、止まる場所も伝える文面も変えるべきだった。

**塞ぎ方**: `claude-routine.sh` が最終結果の本文を見て認証の失敗を切り分け、
専用の文面（`/login` の案内と refresh token の期限）を出してその場で終える。
セッションが動いていない以上、救い出す成果は無いので、退避・巻き戻しの工程には
入らない。あわせて起動前に refresh token の期限を見て、失効済み・7日以内なら
WARNING を出す（**止めはしない**——判定できないことを理由に収集を止めるほうが
害が大きい、という他のゲートと同じ倒し方）。

## 2026-09-04 20:50 lives —— 計器が別のセッションを読み、余力を残したまま「撤退」した

同じ日の 02:30 の回（上）が利用上限で死んだあとの再実行。今度は9分・$1.64 で
「成功」して終わり、コミットまで通った。中身は**検索0回・取得0回、サブエージェント
起動0体**である。やったのは、02:30 の回が `temp/` に残したJSONLの回収（77行の追記）と
終了工程だけだった。

モデルの最終報告にはこう書かれている。

> 起動時の予算表示は文脈再送44.8Mで「撤退の手順に入ってください」を示していたため、
> **新しい調査（Agent起動）は一切行わず**、終了工程のみを実行した。

**その44.8Mは、このリポジトリで同時に動いていた対話セッションの数字だった。**
`weekly-routine/SKILL.md` は起動時に `!` 埋め込みで `budget.py --report` を実行する
——セッション開始の最初期で、**自分の記録がまだディスクに無い瞬間**である。当時の
`transcript_files()` は、IDで引けないとき「同じプロジェクトでいちばん新しい `.jsonl`」に
フォールバックしていた。そこに居たのが対話セッション（当時44.8M）で、`--report` は
そのまま「**撤退の手順に入ってください**」を文脈の先頭に載せた。

    20:50:1x  スキル展開の ! 埋め込み → 文脈再送 44.8M・「撤退の手順に入ってください」
    20:50:22  モデル自身が --report を叩く → 文脈再送 0k（このときは正しく引けている）
    20:51:02  モデルが budget.py のセッション解決部を読みに行く（矛盾に気づいている）
    20:52:39  temp/ に残る 02:30 の回のJSONLを発見、回収に方針転換
    20:57:55  77行を追記（--init は通っていない）
    20:59:56  終了。commit・push

**フォールバックの理由づけ「ルーチンはロックで同時実行を禁じているので取り違えは
起きない」が誤りだった。** あのロックが防ぐのはルーチン同士だけで、人が同じ
リポジトリで対話セッションを開いている場合は防げない。深夜2:30の実行では
表面化しなかっただけである。

もう一つ、**この回を誰も止められなかった**。既存の門はすべて「使いすぎ」の天井で、
「調べなさすぎ」の床が無い。`validate_data.py` は行が壊れていないので ERROR 0、
`diff_data.py` は回収した77行を「新規」と数えて空回りではないと判定、
`report_stats.py --check-fresh` は当時 `FRESH_FLOOR` が events にしか無く常に exit 0。
結果、先週の87行と中途半端な77行（`onsale_start`/`onsale_end` は0%、`official_url` 1%）が
「週次データ更新」としてコミット・push された。

**塞ぎ方**: 4つを行った。

1. `budget.transcript_files()` のフォールバックを廃止。**自分のセッションを同定
   できないときは何も答えない**（`--report` は「文脈再送 未計測」と明示し、
