# 収集スキルへの改善提案（適用は人間が判断する）

## この文書の役割

週次の収集タスクは、**名簿（`data/spots.csv` `data/venues.csv` `data/theaters.csv`
`data/festivals.csv`）を自分で更新してよい**が、**スキル本文（`.claude/skills/*/SKILL.md`）
は書き換えてはならない**。理由は `docs/COLLECTION-PROTOCOL.md` 第7.1節に書いてある。

散文側を変えたほうがよいと気づいたときは、ここに追記する。適用するかどうかは人間が
判断し、適用したら「適用済み」に移す。

## 書き方

実行日の見出しの下に、次の形で1件ずつ書く。**「気づいた」だけでなく、
何を根拠にそう思ったかを書くこと。**根拠のない提案は判断できない。

```markdown
### YYYY-MM-DD /kanto-xxx-collector

- **[対象]** 変えたい箇所（SKILL.md の章名・行の内容）
  - **現状**: いま何と書いてあるか
  - **観測**: 実行中に何が起きたか（件数・失敗の内容・所要時間など、具体的に）
  - **提案**: どう変えるか
```

## 提案してよいもの / いけないもの

|                                                | 例                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **提案してよい**                               | 目標件数・カテゴリ配分が実態に合わない／参照先サイトが閉鎖した・新しい有力なサイトが現れた／季節キーワード表の更新／プレイガイド・配給会社リストの更新／CSVの列や検証ルールに実務上の無理がある／手順の順序が非効率                                                                                      |
| **提案は書いてよいが、自分で変えてはいけない** | 上記すべて（**書き換えは必ず人間が行う**）                                                                                                                                                                                                                                                               |
| **提案自体を慎重にすべきもの**                 | 「推測で埋めない」「確認していない価格・日付を書かない」「転売サイトを使わない」「画像を収集しない」といった**禁止事項の緩和**。これらは調査が難航したときに緩めたくなるが、緩めたい気持ちが生じること自体は緩めてよい理由にならない。提案するなら、緩めても利用者に実害が出ないと言える根拠を添えること |

## 未適用の提案

### 2026-08-04 movies: `screening_type` に「旧作の記念リバイバル全国公開」の置き場がない

- **観測**: 『ハリー・ポッターと賢者の石』25周年記念再上映、『カーズ』20周年記念リバイバル上映のように、シネコンチェーン全国で期間限定再上映される旧作が複数見つかった。これは実質的に「新作ロードショー」と同じ配給形態（`theater`列にチェーン名を書き、特定劇場を指さない）だが、`new`＝「新作公開」という定義には厳密には当てはまらない。かといって`revival`は「名画座・ミニシアターでのリバイバル上映」と定義されており、シネコン全国展開とは前提が異なる。今回は表示仕様（`theater`列の書き方はチェーン名か特定劇場かで決まる）を優先し`new`として収録したが、`screening_type`の定義文だけを見ると誤りに見えるおそれがある。
- **提案**: `new`の定義文に「公開25周年等の記念で全国のシネコンチェーンが期間限定再上映するタイトルを含む」旨を一行加える、または`screening_type`に`rerelease`（全国チェーン再上映）を新設して`revival`（名画座・単館のリバイバル）と分離する。

### 2026-08-04 movies: 複数劇場にまたがる「特別上映」の`theater`列の書き方に迷う

- **観測**: 『王様戦隊キングオージャー フィルム・コンサート in シネマ』（全国20館限定、参加劇場は個別発表）のように、`special`のはずなのに単一劇場に紐づかないイベントがあった。SKILL.mdの表は「`special`＝具体的な劇場名を書く」と明記しているが、20館規模の限定展開では代表1館を書くと「そこでしか観られない」という誤解を生む。今回は参加劇場を確認しきれなかったこともあり収録を見送ったが、今後同様のケースに当たったときの書き方（チェーン名を書いてよいか、あるいは`new`寄りの扱いにするか）が明文化されていない。
- **提案**: 「`special`のうち、複数劇場にまたがる全国限定展開（コンサート上映等）は、`new`と同様にチェーン名（または「◯◯館限定」の注記）を`theater`に書いてよい」という例外規定を追記する。

## 適用済み

### 2026-08-06 3スキル共通＋ルーチン：完走の条件を明文化し、git 操作をスクリプトへ移した

- **[対象]** 各 SKILL.md に「完走条件」章を新設／`docs/COLLECTION-PROTOCOL.md` に第10章「完走」を追加／`.claude/routines/event.txt` と `.claude/scripts/claude-routine.sh` を改訂
- **観測（3つ）**
  - **2026-08-04 movies**: 検索が上限200回に達した時点で調査が止まり、終了工程（`--dispose`・`--gc`・`diff_data.py`・`validate_data.py`・報告）まで到達しなかった。SKILL.md には「打ち切ったら報告に書く」とはあったが、**「打ち切っても終了工程は通す」とは書かれていなかった**。予算の章は「調査をどこでやめるか」しか決めておらず、「セッションをどこで終えてよいか」は未定義だった
  - **`--init` 直後の中断**: `data/*.csv` がヘッダーだけの状態で残ると、翌週の `--init` がそれを「前回分」として `.prev` に退避し、差分検知（静かな欠落の検出）が土台から効かなくなる。仕組みとしての歯止めが無かった
  - **git 操作の置き場所**: `git pull`（最初）と `git push`（最後）を `routines/event.txt` に書いていた＝Claude 自身にやらせていた。途中で終わった回は pull も push も実行されず、逆に**検証を通っていないデータでも push できてしまう**余地があった。またスクリプトは作業ディレクトリとして `.claude` を渡しており、`python3 tools/...` や `data/` が解決できない状態だった
- **適用**
  - 3スキルに**「完走条件」章**を新設。終了工程6つを表で示し、**すべてローカルのコマンドで検索を1回も使わない**ことを明記した（＝予算が尽きていても必ず実行できる）
  - **「撤退の手順」**を規定。打ち切りは中断ではなく終了工程へ進むこと、と定義し、未追記の行を書き切る→未処理の前回行を持ち越しまたは `notfound` で片付ける→終了工程、という順序を固定した。発動条件（工程の枠切れ／検索の合計150回／コンテキスト逼迫／情報源に到達できない）も明示した
  - **「やってはいけない終わり方」**を列挙（`--init` 後の放置・コンテキストに溜めたまま終了・検証を通さず終了・報告なし）
  - 工程の区切りで **`[進捗]` の1行**を出すことを義務化（自動実行のログで、どこまで進んだかを人間が判別できるようにするため）
  - 品質チェックに「完走」ブロックを追加し、「実行手順まとめ」に終了工程の範囲を注記した
  - `routines/event.txt` から git 操作を削除し、**`scripts/claude-routine.sh` が実行前に `fetch` + fast-forward、実行後に検証、通ったときだけ commit / push** する形に変更した。通らなかった回は生成物を `.claude/logs/failed/` に退避して `data/` `docs/` を元に戻す（＝壊れたデータを push しないことを、指示文ではなく仕組みで担保する）
- **注記**: 「予算が尽きたら下から捨てる」（第8.4節）は変えていない。変えたのは**捨て方**であり、捨てた後に終了工程を通すことを必須にした点である

### 2026-08-06 3スキル共通：検索回数の予算を明文化した

- **[対象]** 各 SKILL.md に「調査予算」章を新設し、`docs/COLLECTION-PROTOCOL.md` に第8章「調査予算」を追加
- **観測（2つ）**
  - **2026-08-04 movies**: WebSearch がセッション上限200回に達し、公開日だけ確認できて上映劇場・公式URLまで確認しきれない作品が多数残った（`url` が必須列のため収録を断念）。「未適用の提案」に挙がっていた項目を、ここで解消した
  - **2026-08-02 events**: 126件に対しA群11サイトの横断比較を指示どおり行った結果、`price_best` を書けたのは**7件**、`coupon_note` は**2件**。しかもその7件は**すべて `best_source=公式`（他経路が安かった行は0件）**。名目上1,300回規模の取得に対して、得られた情報は「公式が最安」が7件だけだった
  - **名簿のURL**: `spots.csv` 230/234・`venues.csv` 72/72・`theaters.csv` 85/85・`festivals.csv` 13/14 に `url` が入っているのに、SKILL.md は施設名での検索を指示していた。名簿を一周するだけで上限に達する計算だった
- **適用**
  - `roster.py --list --urls` を追加し、3スキルとも**名簿のURLに直行する**手順に変更（施設・会場・劇場の調査は検索0回で回る）
  - **工程ごとの検索の枠**を表で明示（合計170回・上限200に対し30回の余裕）。工程内で数えれば合計は上限に収まる
  - **行の充足条件（Definition of Done）**を明文化。必須列が揃った行は打ち切る。補助列（`kana` `series_id` `announced_date` 等）のために追加の検索をしない
  - `lat`/`lng`・`parking`/`nearest_station` は**名簿と前回値から自動補完される**ので調べない、と明記（events は「毎回一度は調べよう」、lives は「行ごとに列は必ず埋める」と書いてあり、実装と食い違っていた）
  - events の価格比較を**4段階の打ち切り制**に変更（第0段階＝無料・変動価格・ホール公演は比較しない／第2段階で差が出なければ打ち切り／第3段階は差が出た行だけ）。**クーポンページはセッションに1回ずつ**開く
  - movies のポスターを**1作品1回**に制限、名画座のみを回る（シネコン店舗の個別調査は `theater` がチェーン名である以上、書ける情報を増やさない）
  - lives のツアーで**公演ごとに確認し直すのは受付状況と限定枠だけ**と明記
  - **予算が尽きたときに捨てる順**と、tier C を前回値で持ち越す条件（`status`/`rank` は再計算、`price_checked` は前回の日付のまま、`onsale_*` は空欄）を規定
  - `append_rows.py` の会場属性の補完を、**今回のセッションで既に書いた行からも引ける**ように修正（初出の会場でツアー2公演目以降を書き写す必要が無くなった）
- **注記**: 「全件拾う」対象を「上映劇場が具体的に確認できる作品」に限る、という下記の提案も、この適用の一部として movies の「『新作は全件』の現実的な線引き」章に取り込んだ。**価格比較の網羅性は、A群全サイトから段階制へ実質的に引き下げている。** 上の実測（収穫7件・値引き0件）を根拠としたが、これは禁止事項ではなく網羅性の基準の変更なので、**次回以降の実行で「第3段階まで進んだ件数」を報告させ、この判断が正しかったかを人間が検証できるようにしてある**
