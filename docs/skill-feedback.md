# 収集スキルへの改善提案（適用は人間が判断する）

## この文書の役割

週次の収集タスクは、**名簿（`data/spots.csv` `data/venues.csv` `data/theaters.csv`
`data/festivals.csv`）を自分で更新してよい**が、**スキル本文（`.claude/skills/*/SKILL.md`）
は書き換えてはならない**。理由は `docs/COLLECTION-PROTOCOL.md` 第7.1節に書いてある。

散文側を変えたほうがよいと気づいたときは、ここに追記する。適用するかどうかは人間が
判断し、適用したら「適用済み」に移す。

## 書き方

実行日の見出しの下に、次の形で1件ずつ書く。**「気づいた」だけでなく、
何を根拠にそう思ったかを書くこと。**根拠のない提案は判断できない。

**観測の材料は毎回の実行で手に入る。** `python3 tools/report_stats.py`（中核列の充足率と前回比）と
`python3 tools/budget.py --report --verbose`（工程別の消費・残り時間）の出力をそのまま引くのが
最も強い根拠になる。とくに**充足率が前回より落ちた列**は、ここに書くべきことが実在する合図である。

```markdown
### YYYY-MM-DD /kanto-xxx-collector

- **[対象]** 変えたい箇所（SKILL.md の章名・行の内容）
  - **現状**: いま何と書いてあるか
  - **観測**: 実行中に何が起きたか（件数・失敗の内容・所要時間など、具体的に）
  - **提案**: どう変えるか
```

## 提案してよいもの / いけないもの

|                                                | 例                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **提案してよい**                               | 目標件数・カテゴリ配分が実態に合わない／参照先サイトが閉鎖した・新しい有力なサイトが現れた／季節キーワード表の更新／プレイガイド・配給会社リストの更新／CSVの列や検証ルールに実務上の無理がある／手順の順序が非効率                                                                                      |
| **提案は書いてよいが、自分で変えてはいけない** | 上記すべて（**書き換えは必ず人間が行う**）                                                                                                                                                                                                                                                               |
| **提案自体を慎重にすべきもの**                 | 「推測で埋めない」「確認していない価格・日付を書かない」「転売サイトを使わない」「画像を収集しない」といった**禁止事項の緩和**。これらは調査が難航したときに緩めたくなるが、緩めたい気持ちが生じること自体は緩めてよい理由にならない。提案するなら、緩めても利用者に実害が出ないと言える根拠を添えること |

## 未適用の提案

### 2026-08-23 /kanto-event-collector

- **[対象]** 「価格比較とクーポン検知」章・第2〜3段階（`asoview!` `Klook` `KKday` での価格確認）
  - **現状**: 「商品・プランページまで開いて、その券種の金額を確認する」と指示している
  - **観測**: `tools/fetch_page.py --text` でも `WebFetch` でも、`asoview.com` のチケット商品ページ（`/item/ticket/...` `/channel/tickets/...`）は本文が0〜数百文字しか取れず、実際の販売価格はJavaScriptで描画されておりどちらのツールでも取得できなかった（例: `https://www.asoview.com/item/ticket/ticket0000015499/` は本文0文字）。`Klook` はそもそも `HTTP 403` を返す。結果、価格が一致するかの確認は `asoview.com/base/...`（施設紹介ページ）に載っているSEO用の説明文中の価格表記に頼るしかなく、それすら常に載っているとは限らない。今回338件中、対象層のうち第2段階まで進められたのは7件（うち金額を確認できたのは5件）で、下限15件に届かなかった
  - **提案**: 第2〜3段階の実行手段を「商品ページを開いて確認する」から「施設紹介ページ（`/base/...`）のSEO説明文に載っている価格を確認する」に明示的に緩和するか、もしくはこの2サイトを価格比較の対象から外し、価格がテキストとして取得できるサイト（プレイガイド系: イープラス・チケットぴあ等）に絞ることを検討してほしい。SKILL.md自身が「実測でも price_best は113件中6件（5%）」と書いており、今回の観測はその原因の一端がツール側のJS依存にあることを裏付けている

- **[対象]** 「目標件数」章・「東京は全体の半分程度まで」の基準
  - **現状**: 「東京に偏りすぎないようにすること（東京は全体の半分程度まで）」とある
  - **観測**: `data/spots.csv` の登録施設は東京103件・神奈川39件・埼玉20件・千葉22件・茨城18件（東京が全体202件の51%）。名簿を一巡するだけで東京が自然に過半数へ寄るため、今回のように名簿を全件巡回する回（338件収集、うち東京194件=57%）では「半分程度」に収めるには東京の一部を意図的に間引く必要がある。今回は間引かず全件を収集した
  - **提案**: 目標が「名簿の構成比を反映する」なのか「利用者体験として都県バランスを優先する」なのかを明確にし、後者なら「東京は上限◯件」のような具体的な上限を設けるか、名簿の追加時に都県間のバランスを意識する運用に変えることを検討してほしい
