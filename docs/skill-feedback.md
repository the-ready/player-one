# 収集スキルへの改善提案（適用は人間が判断する）／自己修正ログ

## この文書の役割

週次の収集タスクは、**名簿（`data/spots.csv` `data/venues.csv` `data/theaters.csv`
`data/festivals.csv`）を自分で更新してよい**が、**目標件数・品質基準・禁止事項
（`.claude/skills/*/SKILL.md` の散文のルール）は書き換えてはならない**。理由は
`docs/COLLECTION-PROTOCOL.md` 第7.1節に書いてある。

それらに触れない**小さなバグ**（誤字脱字、壊れたコマンド例、古いパス・URLの参照、
`tools/*.py` の些末な不具合など）は、収集タスク自身が SKILL.md・`tools/`・対応する
設計文書を直接修正してよい。ただし**直した内容は「自己修正ログ」に記録すること**——
散文の書き換えは差分が読みにくく、記録が無いと誰も気づけないためである
（`docs/COLLECTION-PROTOCOL.md` 第7.1節・理由3）。

それ以外——目標件数・品質基準・禁止事項に触れる変更、手順やコードの大幅な改良——を
変えたほうがよいと気づいたときは、ここに提案として追記する。適用するかどうかは人間が
判断し、適用したら「適用済み」に移す。

## 書き方

実行日の見出しの下に、次の形で1件ずつ書く。**「気づいた」だけでなく、
何を根拠にそう思ったかを書くこと。**根拠のない提案は判断できない。

**観測の材料は毎回の実行で手に入る。** `python3 tools/report_stats.py`（中核列の充足率と前回比）と
`python3 tools/budget.py --report --verbose`（工程別の消費・残り時間）の出力をそのまま引くのが
最も強い根拠になる。とくに**充足率が前回より落ちた列**は、ここに書くべきことが実在する合図である。

```markdown
### YYYY-MM-DD /kanto-xxx-collector

- **[対象]** 変えたい箇所（SKILL.md の章名・行の内容）
  - **現状**: いま何と書いてあるか
  - **観測**: 実行中に何が起きたか（件数・失敗の内容・所要時間など、具体的に）
  - **提案**: どう変えるか
```

## 提案してよいもの / いけないもの

|                                                | 例                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **提案してよい**                               | 目標件数・カテゴリ配分が実態に合わない／参照先サイトが閉鎖した・新しい有力なサイトが現れた／季節キーワード表の更新／プレイガイド・配給会社リストの更新／CSVの列や検証ルールに実務上の無理がある／手順の順序が非効率                                                                                      |
| **提案は書いてよいが、自分で変えてはいけない** | 上記すべて（**書き換えは必ず人間が行う**）                                                                                                                                                                                                                                                               |
| **提案自体を慎重にすべきもの**                 | 「推測で埋めない」「確認していない価格・日付を書かない」「転売サイトを使わない」「画像を収集しない」といった**禁止事項の緩和**。これらは調査が難航したときに緩めたくなるが、緩めたい気持ちが生じること自体は緩めてよい理由にならない。提案するなら、緩めても利用者に実害が出ないと言える根拠を添えること |

## 自己修正ログ（小さなバグ）

**目標件数・品質基準・禁止事項に触れない小さなバグ**を自分で直したときは、
提案としてではなく、ここに実施ログとして残す（人間の判断待ちではなく、直した事実の記録）。

```markdown
### YYYY-MM-DD /kanto-xxx-collector（自己修正）

- **[対象]** 直したファイルと箇所（SKILL.md の章名／`tools/xxx.py` の関数名／`docs/*.md` の節番号）
  - **バグの内容**: 何がどう壊れていたか
  - **修正内容**: どう直したか
  - **確認**: `python3 tools/validate_data.py` 等、既存の検証が通ることを確認したか
```

自分の判断が「小さなバグ」の線を越えていないか迷ったら、越えている側として扱い、
このログではなく上の「未適用の提案」に書く。

### 2026-09-21 /kanto-event-collector（適用日: 2026-09-22）

- **[対象]** 「エリア軸の探索」「横断サイトでの補完」ステップ（新規発見）が、同じ週の「施設ベースの網羅調査」（既存行の再確認・`_carry`persist）で**同じイベントを扱っていることを検知しない**設計、および「価格比較とクーポン検知」第1段階の会場ページ確認を**会場ごとに1回で済ませてよい**という説明が、複数の展覧会がある会場では**1回で済ませてよい**と誤読されうる書き方になっている点
  - **観測**: `data/events.csv` の重複調査（`git log -S` での追跡）で、2026-08-30の週次実行（commit `9fbae71`）1回の中で、同一の展覧会が**2つの経路から二重に書き込まれていた**ことを確認した。たとえば東京都美術館の「大英博物館日本美術コレクション」展は、
    - 経路A（既存行の再確認・持ち越し）: 前週から続く行として `price_checked=2026-08-22`（前週の確認日のまま）・`pref=tokyo`・`一般2,300円`という整形済みの価格・展覧会個別ページへの深いURL・100字超の具体的な`desc`を維持したまま書き戻された
    - 経路B（同じ実行内での新規発見）: 直後に同じ会場・同じ会期のイベントとして**別のidで新規行として追記**され、`pref`が空欄、`price`が`2300`ではなく`2600`という**裸の数字**（円表記なし）、`price_checked=2026-08-30`（今回の日付）、`desc`が「大英博物館所蔵の日本美術展」という10数字のテンプレ的な一文、`url`/`official_url`が展覧会個別ページではなく**会場のトップページ**という、第1段階の基準を満たさない行だった

    同じ実行・同じ会場で**別の展覧会**（「この場所の風景―上野・大牟田・ブエノスアイレス」）にも、経路Bで**全く同じ`2600`という価格**が付いていた（正しい価格は`1,200円`）。会場トップページに載っていた何らかの数字（友の会年会費・共通券など、個別の展覧会の観覧料ではない値の可能性が高い）を、会場内の複数の展覧会に使い回したとみられる。同様のパターンが東京都写真美術館（出光真子展）・江戸東京博物館（浮世へのいざない展）でも確認でき、この週だけで4組の重複・劣化行が生まれていた。これらは`uid`（タイトル・会場・日付の正規化キー）がタイトルの表記差（「東京都美術館開館100周年記念」等のプレフィックス有無）で一致しなかったため、`append_rows.py`の重複検知をすり抜け、3週間以上（`data/events.csv`が362件になるまで）気づかれずCSVに残り続けた

  - **推定原因**: 週次実行の中で「既存行の再確認」（名簿・前回CSVのURLに直行して深掘りする）と「エリア軸の探索」「横断サイトでの補完」（会場・地域を横断して新規イベントを探す）が別ステップ・別サブエージェントとして走る設計上、後者は前者が同じ週内で何を確認済みかを見ておらず、`uid`の完全一致以外に重複を防ぐ手段がない。加えて、新規発見側は「会場ページを1回開けば会場の全イベントに効く」という第1段階の説明（346行目付近）を、**会場のどのページでもよい**という意味に取り違えると、個別の展覧会ページを開かずトップページの数字を使い回してしまう。この経路で書かれた行は、通常の第1段階（`料金`/`入館`等のリンクを辿って個別ページを開く）を経ていないため、価格・desc・pref のすべてで基準未達になりやすい
  - **提案**:
    1. `validate_data.py`に、`price`が**単位（円）を含まない裸の数字だけ**（正規表現 `^\d+$`）になっている行をWARNINGで挙げるチェックを追加する。「価格は整形して書く」というルールは散文にはあるが機械チェックが無く、今回の劣化行はこの1チェックだけで書いた瞬間に気づけたはずである
    2. `validate_data.py`または`diff_data.py`に、**同一CSV内**で「同じ`venue`・会期が重なる・タイトルの類似度が高い」組をWARNINGで挙げるチェックを追加する（`diff_data.py`が「消滅」検知に既に使っているあいまい照合のロジックを、週をまたぐ比較ではなく同じCSV内の突き合わせに転用できる）。今回はこの手作業の突き合わせに何十回もの`grep`と目視が必要だったが、実装すれば収集の最終工程（`report_stats.py --check`と同じタイミング）で自動的に拾える
    3. 「価格比較とクーポン検知」第1段階の説明に、「会場ページを1回開けば全イベントに効く」のは**同一の展覧会・企画に属する複数行**（会期のセクション違いなど）に限られ、**会場内の別の展覧会・企画は個別に料金ページ・商品ページを確認すること**という一文を明記する
