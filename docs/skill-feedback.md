# 収集スキルへの改善提案（適用は人間が判断する）

## この文書の役割

週次の収集タスクは、**名簿（`data/spots.csv` `data/venues.csv` `data/theaters.csv`
`data/festivals.csv`）を自分で更新してよい**が、**スキル本文（`.claude/skills/*/SKILL.md`）
は書き換えてはならない**。理由は `docs/COLLECTION-PROTOCOL.md` 第7.1節に書いてある。

散文側を変えたほうがよいと気づいたときは、ここに追記する。適用するかどうかは人間が
判断し、適用したら「適用済み」に移す。

## 書き方

実行日の見出しの下に、次の形で1件ずつ書く。**「気づいた」だけでなく、
何を根拠にそう思ったかを書くこと。**根拠のない提案は判断できない。

```markdown
### YYYY-MM-DD /kanto-xxx-collector

- **[対象]** 変えたい箇所（SKILL.md の章名・行の内容）
  - **現状**: いま何と書いてあるか
  - **観測**: 実行中に何が起きたか（件数・失敗の内容・所要時間など、具体的に）
  - **提案**: どう変えるか
```

## 提案してよいもの / いけないもの

|                                                | 例                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **提案してよい**                               | 目標件数・カテゴリ配分が実態に合わない／参照先サイトが閉鎖した・新しい有力なサイトが現れた／季節キーワード表の更新／プレイガイド・配給会社リストの更新／CSVの列や検証ルールに実務上の無理がある／手順の順序が非効率                                                                                      |
| **提案は書いてよいが、自分で変えてはいけない** | 上記すべて（**書き換えは必ず人間が行う**）                                                                                                                                                                                                                                                               |
| **提案自体を慎重にすべきもの**                 | 「推測で埋めない」「確認していない価格・日付を書かない」「転売サイトを使わない」「画像を収集しない」といった**禁止事項の緩和**。これらは調査が難航したときに緩めたくなるが、緩めたい気持ちが生じること自体は緩めてよい理由にならない。提案するなら、緩めても利用者に実害が出ないと言える根拠を添えること |

## 未適用の提案

### 2026-08-10 3スキル共通: WebFetch が実行環境のegressプロキシで全ドメインブロックされていた

- **[対象]** SKILL.md の調査手順全般（劇場公式サイト・配給会社サイトへの直接アクセスを前提にしている箇所）
- **現状**: 「名簿のURLに直行する」「作品公式サイトまで辿ってOGP画像を拾う」など、複数の章がWebFetch（URL直接取得）でのアクセスを前提に書かれている
- **観測**: このセッションでは `WebFetch` を呼ぶと全ドメインで `EGRESS_BLOCKED`（`curl -sS http://127.0.0.1:33283/__agentproxy/status` の `recentRelayFailures` には記録されず、プロキシ手前でツール自体がブロックしている様子）になり、`data/theaters.csv` に載っている85件のURLも含め一切取得できなかった。`WebSearch` は正常に動作したため、今回は全面的に検索の要約だけで代替した。結果として、poster_url は実在確認ができず117件すべて空欄になった（画像を1件も収集できなかった週は初めて）。日付・料金も検索結果の要約に依存したため、通常よりも「確認できなければ空欄」に倒す判断が増えた
- **提案**: 実行環境によってWebFetchが使えないケースがあることを踏まえ、SKILL.mdの「調査予算」章に一言「WebFetchが使えない環境ではWebSearchの要約で代替してよい」と明記してはどうか。あわせて、次回以降の実行担当（人間・エージェント問わず）が同じ状況に遭遇した際に「壊れている」と誤診して作業を止めてしまわないよう、`docs/COLLECTION-PROTOCOL.md` あたりに切り分け手順（`curl .../\_\_agentproxy/status` を見る、WebSearchは動くかを先に試す）を書いておくと復旧が早いかもしれない

### 2026-08-04 movies: `screening_type` に「旧作の記念リバイバル全国公開」の置き場がない

- **観測**: 『ハリー・ポッターと賢者の石』25周年記念再上映、『カーズ』20周年記念リバイバル上映のように、シネコンチェーン全国で期間限定再上映される旧作が複数見つかった。これは実質的に「新作ロードショー」と同じ配給形態（`theater`列にチェーン名を書き、特定劇場を指さない）だが、`new`＝「新作公開」という定義には厳密には当てはまらない。かといって`revival`は「名画座・ミニシアターでのリバイバル上映」と定義されており、シネコン全国展開とは前提が異なる。今回は表示仕様（`theater`列の書き方はチェーン名か特定劇場かで決まる）を優先し`new`として収録したが、`screening_type`の定義文だけを見ると誤りに見えるおそれがある。
- **提案**: `new`の定義文に「公開25周年等の記念で全国のシネコンチェーンが期間限定再上映するタイトルを含む」旨を一行加える、または`screening_type`に`rerelease`（全国チェーン再上映）を新設して`revival`（名画座・単館のリバイバル）と分離する。

### 2026-08-04 movies: 複数劇場にまたがる「特別上映」の`theater`列の書き方に迷う

- **観測**: 『王様戦隊キングオージャー フィルム・コンサート in シネマ』（全国20館限定、参加劇場は個別発表）のように、`special`のはずなのに単一劇場に紐づかないイベントがあった。SKILL.mdの表は「`special`＝具体的な劇場名を書く」と明記しているが、20館規模の限定展開では代表1館を書くと「そこでしか観られない」という誤解を生む。今回は参加劇場を確認しきれなかったこともあり収録を見送ったが、今後同様のケースに当たったときの書き方（チェーン名を書いてよいか、あるいは`new`寄りの扱いにするか）が明文化されていない。
- **提案**: 「`special`のうち、複数劇場にまたがる全国限定展開（コンサート上映等）は、`new`と同様にチェーン名（または「◯◯館限定」の注記）を`theater`に書いてよい」という例外規定を追記する。

### 2026-08-09 3スキル共通: `~/.claude/skills/` の複製が古く、書き出し先が `data/` の外を指している

- **[対象]** スキル本文ではなく**実行環境の同期**（`.claude/skills/` → `~/.claude/skills/`）

  - 列がイベント24列・映画23列（現在は45列・46列）

  - イベントの説明文が旧プロダクト名「今日とこれからのイベント」と旧ファイル名 `event_departure_board.html` のまま

## 適用済み

### 2026-08-10 movies: ポスター収集で `curl` による生HTML直接取得を正式な手段として追加（**後に失効**）

> **この項は失効している。** 3タブとも画像を扱わない方針になり、ポスター収集の工程そのものが無くなった（設計書 第7.1節）。`curl` で生HTMLを取れるという観測自体は他の用途にも当てはまるので、記録としては残す。

- **[対象]** `.claude/skills/kanto-movie-collector/SKILL.md`「ポスター画像の取り扱い」章
- **観測**: `poster_url` 空欄128行を対象にしたポスター専念セッションで、`curl`で生HTMLを直接取得し `og:image` metaタグ／`<img>`タグを正規表現で抜く方式を使ったところ、WebFetch（HTMLをmarkdown化するため`<head>`情報が失われる）より確実に取得でき、しかもBashツール経由のためWebSearch/WebFetchの検索予算を一切消費しなかった。結果として95件（公式63／配給会社21／TMDb14）を確定でき、使用したWebFetch呼び出しは36回に留まった。一方Disney/Searchlight/20th Century系ドメインはcurl・WebFetch双方でbot対策により403を返し取得不可だった
- **適用**: 「ポスター画像の取り扱い」章に「curlで生HTMLを直接取得する方法」の節を新設。手順（`curl`コマンド例）、**予算を消費しない代わりに対象ドメインの`robots.txt`を毎回確認すること**（`tools/check_robots.py`は`data/sources.json`の固定名簿しかカバーしないため、映画公式サイトのように毎週ドメインが変わる相手には別途手動確認が要る旨を明記）、Disney系ドメインでの403の既知の制約、を書いた

### 2026-08-10 movies: `poster_url` 収集のWebFetchプロンプトを「og:image」から「メインビジュアル画像」に変更（**後に失効**）

> **この項は失効している**（上と同じ理由）。WebFetchが`<head>`のmetaタグを渡さないという観測は、他の用途では引き続き有効。

- **[対象]** `.claude/skills/kanto-movie-collector/SKILL.md`「ポスター画像の取り扱い」章の「予算 —— 1作品につき1回」節
- **観測**: 2026-08-10のセッションで、`bluelock-movie.jp` `tokizan.jp` `kao-movie.com` `madoka-magica.com/wr/` `sekiro-anime.jp` `anime-eupho.com` `tokyomer-movie.jp` の7サイトに「og:image meta タグの絶対URLを教えて」という趣旨のプロンプトでWebFetchを呼んだところ、**7件とも「headセクションが渡されていないので分からない」という同じ失敗**になった（WebFetchがHTMLをmarkdown化してから渡す実装のため、`<head>`内のmetaタグが変換後に残らない模様）。一方「ページに表示されているメインビジュアル画像のURLを教えて」という趣旨に変えた3件（`votoms-gh.com` `happinet-phantom.com/wandance/` `tantei-bar.com`）は、いずれも本文中の`<img>`に対応する相対パスを拾えた
- **適用**: SKILL.md「予算 —— 1作品につき1回」節に一言追記し、「og:image metaタグ」ではなく「ページに表示されているメインビジュアル／キービジュアル画像のURL」を尋ねるようWebFetchプロンプトの聞き方を明記した

### 2026-08-10 movies：TMDbを取得元から全面禁止し、既存14件を空欄化（**後により強い方針に置き換え**）

> **この項は、画像そのものを扱わない方針（設計書 第7.1節）に置き換わった。** ただし `check_robots.py` を `Claude-User`/`Claude-SearchBot` まで見るよう拡張した部分は、画像に限らず3スキルの着手前チェックとして残っている。

- **[対象]** `.claude/skills/kanto-movie-collector/SKILL.md`「ポスター画像の取り扱い」章／`tools/validate_data.py`（`POSTER_SOURCES` `POSTER_DENY_HOSTS`）／`tools/check_robots.py`／`data/sources.json`／`data/movies.csv`／`docs/DESIGN.md` 第7.1節／`README.md`／`index.html` `terms.html` `privacy.html`
- **経緯**: `tools/check_robots.py` を「AI系UAを名指ししているサイトでは `Claude-User`・`Claude-SearchBot`（Anthropicのエージェントによる実行時アクセスに対応するUA。学習データ収集用の`ClaudeBot`とは別物）への許可状況も個別に見る」よう拡張したところ、**TMDb (themoviedb.org) がこの2つを名指しで`Disallow: /`（全面拒否）していた**ことが判明した。ユーザ指示により、TMDbを取得元から完全に禁止することにした
- **適用**: `poster_source`の許可値から`TMDb`を削除（`公式サイト`/`配給会社サイト`の2つのみ）。`validate_data.py`の`POSTER_DENY_HOSTS`に`image.tmdb.org`/`themoviedb.org`を追加し、TMDbの画像URLはどんな`poster_source`を名乗っても機械的にERRORになるようにした。`data/sources.json`からTMDbのエントリを削除。`data/movies.csv`で`poster_source=TMDb`だった14件は`poster_url`/`poster_source`ごと空欄化（`validate_data.py`・`diff_data.py movies`とも終了コード0を確認済み）。ユーザ向け文書（README・index.html・terms.html・privacy.html）からもTMDbの記載を削除
- **注記**: この禁止は画像の性質・利用規約の問題ではなく、**取得手段（Claude-User/Claude-SearchBotとしてのアクセス）そのものをサイト側が拒否している**という、eiga.com系画像禁止（2026-08-09、著作権・規約上の理由）とは種類の違う理由である。同種の判定はこのタスクに限らず起こりうるため、`check_robots.py`を3スキルとも着手前に毎回実行する運用にした（別項）

- **[対象]** `.claude/skills/kanto-live-collector/SKILL.md` の「2. 対象地域」「4. 目標件数」「ステップ1」「ステップ2」「調査予算」「品質チェック」／`docs/DESIGN.md` 第9.2節・第20.9節

  - 隣接県は関東7都県の枠を埋める代わりにはならない、として**全体の1割程度**を上限の目安に置き、品質チェックに項目を足した

### 2026-08-09 3スキル共通：`roster.py --add` に `pref` の検証を入れ、検証側の抜けも塞いだ

- **[対象]** `tools/roster.py` の `do_add` ／ `tools/validate_data.py` の `PREFS` の読み取り
- **適用**: 下記 2026-08-08 の提案どおり、`roster.py --add` が `pref` を `assets/js/config.js` の `PREFS` に照らして検証し、集合外なら `SystemExit` するようにした（`url` 形式の検証の直後）。
- **あわせて見つかった検証側の抜け**: `validate_data.py` が `PREFS` を拾う正規表現は `{ key: "..." }` を**全文から**探しており、`PRESETS`（`today` `weekend` `month`）とタブ宣言（`event` `movie` `live`）まで都県キーとして混ざっていた。つまり `pref` に `today` と書いても検証を素通りする状態で、**提案どおり `roster.py` にこの集合を渡すだけでは検証にならなかった。** `PREFS` の配列だけを見るように直したうえで、両者が同じ `load_prefs()` を使うようにしてある（選択肢の正本は config.js ひとつ、という第15.11節の方針を維持）。
- **注記（2026-08-09 に判断済み）**: `data/venues.csv` の静岡県18会場は `pref="other"` のまま**意図的に残す**。監査ではこれを「関東1都6県（`docs/DESIGN.md` 第9.2節）から外れた名簿の drift」として挙げたが、**意図して入れたものであるとの回答を得た**。
  さらに、名簿に置くだけでは対象地域の規則により永遠にヒットせず `--gc` で自動的に消えてしまうため、**ライブの対象地域そのものを「関東1都6県＋隣接5県」に広げた**（下記の別項）。
  **この行は消さないこと。** 同じ指摘が毎回の監査で蒸し返されるのを防ぐために書いている。

### 2026-08-08 lives: `roster.py --add` が `pref` の値を検証していない（→ 上記で適用済み）

- **観測**: 2026-08-08 のセッション開始時点で `data/venues.csv` に18件（すべて静岡県の会場）、`data/festivals.csv` に1件（FUJI ROCK FESTIVAL）、`pref` が `shizuoka` / `niigata` という、`assets/js/config.js` の8キー（`tokyo` `kanagawa` `saitama` `chiba` `ibaraki` `tochigi` `gunma` `other`）に存在しない値で登録されていた。`validate_data.py` はこれを毎回 ERROR として検出する仕様になっており、**このタスクの誰か（別スキルまたは以前のセッション）がこの状態で `roster.py venues --add` を実行した**ことになる。`tools/roster.py` の `do_add` は `url` の形式は検証する（190行目付近）が、`pref` の値をこの8キーに照らして検証していない。今回は `pref` を `other`（関東以外）に置き換えて ERROR を解消したが、この根本原因（`roster.py` 側の検証漏れ）は残っている。次に同じ経路で関東以外の県名（例：`niigata` `yamanashi`）が紛れ込むと、収集タスクが着手前から ERROR を抱えた状態で始まることになる。
- **提案**: `tools/roster.py` の `do_add`（および将来 `pref` を書き換える操作があれば同様に）に、`validate_data.py` と同じ8キー集合での検証を追加し、集合外の値を渡したらその場で `SystemExit` するようにする。`url` 形式の検証（192-193行目）と同じ位置に足せる。
